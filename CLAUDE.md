# Target — Offline Exam Prep Tracker

## What this app is

A personal, fully offline Android app for organizing exam study materials and tracking study progress. Not tied to any specific exam — the user defines whatever exam(s) they're preparing for, then organizes materials underneath. It's now genuinely multi-account (see below) — "personal" describes the deployment (one phone, not distributed), not a single-user data model.

**The data model was fully reset once already** (see git history around "Full reset" for what came before — nested Topics, Question Banks, Practice Exams, Lecture Notes, Test Attempts, pace estimation). None of that survived the reset; don't resurrect ideas from it without the user asking again. What's described below is the current, second-generation model, now with accounts layered on top.

### Accounts

Real multi-account auth, not a single-profile gate — `Register` can create additional accounts at any time; `Login` looks up by username. `User`: firstName, middleName (optional), lastName, username (unique), email (optional), passwordHash/passwordSalt (`data/PasswordHasher.kt` — salted SHA-256 via `SecureRandom`/`MessageDigest`, no new dependency; passwords are never stored or compared in plaintext), preferredName + preferredNameSource.

**Preferred name** is chosen via a toggle (First / Middle) plus three mutually-exclusive checkboxes (Last Name / Username / Other — "Other" reveals a free-text field), not typed directly — `ui/common/PreferredNameSelector.kt`, shared between Register and Edit Profile. The choice **stays live**: `User.preferredNameSource` is stored, and `data/PreferredNameResolver.kt`'s `resolvePreferredName()` recomputes the stored `preferredName` string from the current source field every time the profile is saved — so editing First Name later automatically updates Preferred Name too, if that's the active source. This is the one place in the app where a value is deliberately kept in sync via recomputation-on-save rather than either a live read-time join or a frozen one-time value.

Session persistence and the light/dark theme preference both live in `data/local/AppPreferences.kt` — a plain `SharedPreferences` wrapper (deliberately not DataStore, no new dependency needed for two small values). `currentUserId` is still read once per ViewModel at construction, not observed reactively — Log Out and Switch Account (see Navigation shell below) both clear/replace it and then force a full back-stack reset (`popUpTo(0)` to `LoginRoute`/`HomeRoute`) rather than relying on any ViewModel noticing the change mid-process, so the "read once" assumption still holds; there just wasn't a codepath that changed it before. `isDarkMode` **is** a `StateFlow`, since `MainActivity` needs to react immediately when Settings toggles it.

`Exam` and `Course` carry a nullable `userId` (FK, cascade) — nullable because real pre-auth exam data already existed on-device with no owner when accounts were added; those rows just don't appear once list queries filter by the logged-in user, rather than being destroyed. Every exam/course query and insert must be scoped by `AppPreferences.currentUserId` — there is no global, cross-account exam or course data (unlike `ExamType`, which stays a shared/seeded lookup table, not per-user).

### Exam data (unchanged in shape since the last update, now user-scoped)

Hierarchy: **Exam → (optional) Section → Courses**, plus a per-user **Course** pool, a per-user **Language** pool, and a shared, seeded **ExamType** list.

- **ExamType**: a real, seeded table (not an enum) — currently "University Entrance Exam", "High School Entrance Exam", "Language Exam", "Vocational Exam". Seeded idempotently on every app start (`ExamTypeDao.seedDefaultsIfEmpty()`, called from `TargetApplication.onCreate()`) rather than via `RoomDatabase.Callback.onCreate()` — that callback does **not** reliably fire when the schema is created via a destructive-fallback recreation rather than a genuine first-run (confirmed on-device). Managing this list (add/delete/rename by the user) is an explicitly deferred next step — don't build that screen unless asked. Shared across all accounts, not per-user. `ExamTypeDao.kt` exports `LANGUAGE_EXAM_TYPE_NAME` (= "Language Exam") as the one place that magic string lives — everywhere else that needs to know "is this exam a language exam" compares against that constant rather than a re-typed literal.
- **Exam**: name, `examTypeId` (FK), `userId` (FK, nullable — see Accounts), `hasSections: Boolean` (decided at creation, not editable afterward — toggling it later raises unresolved questions about what happens to existing sections/courses), `examDate` (meaningful only when `!hasSections`), optional `studyStartDate`, optional `languageId` (FK to Language, `SET_NULL` on delete — meaningful only when the exam's type is Language Exam; see Language below), optional `level: String?` (schema v16 — meaningful only for a Language Exam, same scoping as `languageId`; see Language below for the full split).
- **Language**: per-user, reusable, free-text name (e.g. "German") — same shape as `Course` minus icons (no icon picker for languages, unlike courses). Has its own full CRUD screen (`ui/languagelist/`, reached from Home's drawer, right after Courses) mirroring `ui/courselist/`'s list/add/edit/delete pattern. `AddOrEditExamDialog` (`ui/common/ExamFormDialog.kt`) shows a Language combobox *only* when the selected exam type's name equals `LANGUAGE_EXAM_TYPE_NAME` — it's not shown for any other exam type, and the dialog nulls out the selection on save if the type gets changed away from Language Exam. The chosen language isn't just stored silently: it also surfaces in `ExamListScreen`'s row subtitle (`examType · language · date`) and `ExamDetailScreen`'s summary (`Language: X`), the same way `examDate` already does, so picking one has visible confirmation after saving. Because deleting a Language `SET_NULL`s any exam's `languageId` that pointed to it, a Language Exam can end up with `languageId == null` two ways (never set, or set-then-deleted) — both render as an explicit "No language set" in the row/summary rather than silently omitting the line, so a Language Exam always shows *some* language state. Non-Language-Exam types never show the line at all, set or not.

**Publisher / Level split**: by explicit request ("German A2 certificate... you take the exam from Goethe. its exam's publisher but your level is A2. lets separate it"), a Language Exam's certifying body and proficiency level — previously crammed into one free-text `Exam.name` (e.g. "Goethe A2" as a single string) — are now two separate concepts: `Exam.name` holds just the publisher ("Goethe"), and the new `Exam.level: String?` (schema v16, plain nullable `ADD COLUMN`, same no-backfill shape as every other added column with no inferable source) holds the level. `level` is **free text, not a fixed CEFR dropdown** — confirmed via clarifying question, since proficiency scales differ by language family (CEFR A1–C2 for German/French/Spanish/Italian, but JLPT N5–N1 for Japanese, HSK 1–6 for Chinese, TOPIK for Korean, etc.) and a fixed European-only dropdown would lock out every non-CEFR language; free text matches how Course/Topic/Study Resource names already work everywhere else in the app. `AddOrEditExamDialog`'s Name field relabels to "Publisher" (`exam_field_publisher`) whenever the selected type is Language Exam (English default: "Exam name" otherwise), and a new optional "Level" text field (`exam_field_level`) appears directly under the Language combobox, only for that same type — `level` is nulled out on save exactly like `languageId` whenever the type isn't Language Exam. Existing real data (e.g. the on-device "Goethe A2" exam, created before this split) isn't retroactively parsed apart — the new column comes back `null` and the exam keeps reading as "Goethe A2" via `name` alone until manually re-split through the edit dialog, the same "orphaned rather than destroyed" precedent as every other schema addition with no reliable source to infer from.

`ui/common/ExamDisplayLabel.kt`'s `examDisplayLabel(exam)` is a small plain (non-`@Composable`, no string resources needed) helper — `"$name $level"` when `level` is set, else just `name` — used everywhere the exam's short label already appeared before this split: `ExamListScreen`'s row headline and `ExamDetailScreen`'s top-bar title. `ExamDetailScreen`'s summary also gained a "Level: X" line (`examdetail_level`) directly under "Language: X", following the exact same "always show *some* state, `common_not_set` fallback, never silently omit the line" convention already established for language.

By the same follow-up request ("show what level exam is that and which language's exam as well like 'Goethe - A2 - German'"), Home's Upcoming card uses a **different, dash-joined, language-inclusive** format instead of `examDisplayLabel` — `HomeViewModel`'s private `homeExamLabel(item: ExamWithType)` builds `listOfNotNull(name, level, languageName).joinToString(" - ")` for a Language Exam (any missing part is simply skipped, not shown as an empty segment), falling back to the plain `name` for every other exam type. This is deliberately scoped to Home only, not applied to `examDisplayLabel` itself, since `ExamWithType` (unlike the plain `Exam` entity) already carries `languageName` from its join, and `ExamListScreen`/`ExamDetailScreen` already surface the language on a separate line of their own — repeating it inline in their title would be redundant there in a way it isn't on Home's single-line Upcoming row. Confirmed on-device against the real Goethe A2 exam (migrated cleanly from v15, `level` read back `null`): the Edit dialog's Name field showed as "Publisher" with "Goethe A2" in it; splitting it to Publisher "Goethe" + Level "A2" and saving correctly updated the summary to show "Level: A2", the screen title back to "Goethe A2" (recombined via `examDisplayLabel`), the Exams list row to "Goethe A2" (subtitle already showing "Language Exam · German · Nov 30, 2026"), and Home's Upcoming card to exactly **"Goethe - A2 - German"**.
- **Course**: per-user, reusable, free-text name (e.g. "Chemistry"), plus an optional `icon` (nullable `String` key, e.g. `"functions"`, `"science"`), a nullable `examTypeId` (FK to `ExamType`, `SET_NULL` on delete) — a course belongs to exactly one exam type (e.g. "Math" only ever lives under University Entrance Exam), fixed at creation but **reassignable later from `CourseDetailScreen`'s edit dialog** (see below) — unlike `Exam.hasSections`, this one deliberately isn't a "decided once" field — and a nullable `category: CourseCategory?` (`QUANTITATIVE`/`VERBAL`, `data/local/entity/CourseCategory.kt`), for University Entrance/High School Entrance/Vocational courses only (Language Exam never has `Course` rows at all — see below). The exam-level "Add course" dialog (`ExamDetailScreen`) shows the user's not-yet-attached courses as a **multi-select checklist** (`ExamDetailViewModel.availableCoursesToAdd`, checked ones added together via `addExistingCourses`) alongside a text field for creating a new course inline (create-if-missing, case-insensitive name match) — both are now scoped to the exam's own `examTypeId`, not the user's whole course pool, so a Vocational exam can never pick up a University-tagged course. It used to be blind free-text entry only — an already-created course had no visible way to be picked, only re-typed exactly — fixed after being reported as a bug. A course created inline this way (or via the section picker) gets no icon *and no category* at creation — both are only assignable from `CourseDetailScreen`'s edit dialog, not speculatively exposed in every place a course can be created. The category field is a 3-segment toggle (Unset / Quantitative / Verbal) — originally its own private `CourseCategoryField`/`CategoryToggleSegment` copy in `CourseDetailScreen.kt` (the third deliberate reuse of the `PreferredNameSelector` segmented-toggle visual shape, matching how the app had handled that pattern twice before), now backed by the shared `ui/common/SegmentedToggle.kt` — see Interface redesign below. `CourseListByTypeScreen`, `ExamDetailScreen`'s Courses pool, and `SectionDetailScreen`'s assigned-courses list all group courses into **Quantitative / Verbal / Uncategorized** sections (in that order, a group only rendered when non-empty) instead of one flat list — added after the flat list was reported as looking "crowded," then extended to sections by explicit request (initially scoped out — see `SectionCourseWithCourse` note below). Each group has its own collapsible header (chevron, default closed, same `KeyboardArrowDown`/`KeyboardArrowUp` pattern as the Courses/Sections sections below) — a `*GroupHeader` composable, one private copy per screen (`courseGroups()`/`CourseGroupHeader` in `CourseListByTypeScreen.kt`, `examCourseGroups()`/`CourseGroupHeader` in `ExamDetailScreen.kt`, `sectionCourseGroups()`/`SectionCourseGroupHeader` in `SectionDetailScreen.kt`), each over its own screen's `Course.category` / join projection's `courseCategory` field. `SectionCourseDao`'s join query and `SectionCourseWithCourse` gained `courseCategory` the same way `ExamCourseWithCourse` did, once the grouping was extended there too.

- **Topics**: per-course, reusable within that course, tracking how many tests/questions a Question Bank study resource covers for each topic — and, since multiple Question Banks (different publishers) can attach to the same topic, how many exist for that topic in total across publishers. `Topic` (`data/local/entity/Topic.kt`): id, name, `courseId`/`languageId` (both nullable FK `CASCADE`, exactly one set — originally `courseId` was the sole non-null FK and Topics were Course-only, until generalized to also support Languages; see the "Topics for Languages" section below for the full story). The join entity `StudyResourceTopic` (`data/local/entity/StudyResourceTopic.kt`) carries the actual counts, one row per (question bank, topic) pair: `studyResourceId`/`topicId` (both FK `CASCADE`, unique compound index), `testCount`/`questionCount: Int` (default 0) — mirrors `ExamCourse`/`SectionCourse`'s join-table shape exactly. `TopicDao.getTopicTotalsByCourseId(courseId)` is the cross-publisher aggregate query (`LEFT JOIN` + `SUM` + `COALESCE`, so a topic with no attachments still shows 0/0 rather than disappearing); `StudyResourceTopicDao.getByTopicId(topicId)` is the per-publisher breakdown query, `getByStudyResourceId(studyResourceId)` lists topics attached to one resource.

- **Practice Sessions**: by explicit request ("track how many tests and questions they've solved... categorized as solved or unsolved... how many minutes or hours it took"), the app now records actual study progress against a `StudyResourceTopic`'s target counts, not just the targets themselves. `PracticeLog` (`data/local/entity/PracticeLog.kt`): id, `studyResourceTopicId` (FK to `StudyResourceTopic`, `CASCADE` — a `StudyResourceTopic`'s unique `(studyResourceId, topicId)` index makes its own `id` a sufficient anchor, the same shape `StudyResourceTopic` itself uses to point at `StudyResource`/`Topic`), `testsSolved`/`solvedCount`/`unsolvedCount: Int` (solved = correct, unsolved = wrong — confirmed via clarifying question, not attempted-vs-skipped), `durationMinutes: Int` (combined from separate Hours/Minutes number inputs at save, not stored as two fields), `loggedAt: Long`. Total questions and a Turkish-exam-style **net score** (`solvedCount - unsolvedCount / 4.0`, confirmed via clarifying question — the standard doğru − yanlış/4 formula) are **derived at display time, never stored**, the same "compute in Kotlin, don't persist a redundant field" convention `TopicDetailViewModel.totalTestCount`/`totalQuestionCount` already established. `PracticeLogDao.getByStudyResourceTopicId` orders by `loggedAt DESC`.

  Tapping a topic row in `StudyResourceDetailScreen`'s Topics list now navigates to `ui/topicprogress/TopicProgressScreen.kt` (`TopicProgressRoute(studyResourceTopicId)`, a back-arrow `Scaffold` drill-down, same exception as `TopicDetailScreen`) instead of opening the old inline "Edit counts" dialog — chosen over an inline dialog by explicit request, since a session log needs room for a running aggregate and history list, not just two numbers. This screen shows: the target counts (`"Hedef: X test · Y soru"`), an aggregate line summing every logged session for this topic+resource pair (tests, solved/unsolved, net score, total time as "Xh Ym"/"Xsa Ydk"), a "+ Log Session" action opening `LogSessionDialog` (five digit-filtered numeric fields — Tests Solved, Solved, Unsolved, Hours, Minutes — the same numeric-input template `StudyResourceTopic`'s original Test/Question Count fields set), and a session history list (most recent first) where tapping a row reopens the same dialog pre-filled for editing, with a "Delete this session" action inside it — mirroring the old `EditTopicCountsDialog`'s "Remove topic" placement precedent (an editable row opens a small editor rather than exposing a bare inline delete icon). Confirmed on-device against the real 13-topic Chemistry Question Bank (schema v12 migrating cleanly from v11): logged a session (3 tests, 20 solved, 5 unsolved, 1h30m) and saw the aggregate line read "3 test · 20 doğru · 5 yanlış · Net 18,75 · Toplam 1sa 30dk" (net correctly computed as 20 − 5/4 = 18.75, Turkish comma-decimal formatting picked up automatically from the active locale the same way `SimpleDateFormat` already does), the session row appeared with the correct date/summary, tapping it reopened the edit dialog exactly pre-filled, Cancel left the data untouched, the target-counts edit dialog and the detach confirmation (correctly reading "...deletes 1 logged session...") both opened correctly, and a WAL-inclusive `.db` pull showed the exact expected row.

  By explicit follow-up request ("it has to limit test and question count to what topic has... if there is a session user has to see what is left"), `TopicProgressScreen` also shows a **Remaining** line (`label_remaining_counts`, target minus every logged session's own tests/solved+unsolved so far, `coerceAtLeast(0)`) right under the existing Target line, and `LogSessionDialog` clamps input live so the cumulative total across all of a topic's sessions can never exceed its target — a 15-test topic can't reach 16 no matter how many sessions get logged against it. The max for each field is computed excluding the *other* sessions' contributions relative to whichever one is being edited (`sessions.filter { it.id != editingSession?.id }.sumOf { ... }`), not the grand total — otherwise editing an existing session would double-count its own prior value against itself and refuse to let it keep its current numbers. Tests Solved clamps directly against its own remaining max; Solved and Unsolved clamp against *each other* since their sum (not either one alone) is what has to stay under the remaining question count — each field's `onValueChange` reads the sibling field's current value to compute its own allowed ceiling. A small `labelSmall` hint under each capped field (or pair) states the live limit (`"En fazla %1$d"` / `"Doğru + yanlış en fazla %1$d"`). Confirmed on-device: Remaining correctly read "Kalan: 12 test · 127 soru" against a target of 15/152 with one logged session of 3/25 already counted; typing "99" into Tests Solved (remaining max 12) clamped live to "12"; Cancel discarded the test input without saving anything, leaving the original session data untouched.

  Progress was still only visible one screen deep (on `TopicProgressScreen` itself), so by explicit follow-up request it now also surfaces a level earlier, in two places. - **Course-level Question Bank CSV export**: `CourseDetailScreen` has a third top-bar action, Export (`Icons.Filled.Share`, between Edit and Delete), by explicit request after manually entering a large Chemistry Question Bank felt tedious enough to want a backup. It's a one-way, scoped export — not a general backup/restore (that stays out of scope; see above) — covering exactly one course's `QUESTION_BANK`-type `StudyResource`s and their attached topics. `CourseDetailViewModel.fetchQuestionBankExportRows(onResult)` filters `StudyResourceDao.getByCourseId` to `type == QUESTION_BANK` in Kotlin (no new SQL — same "filter by type in Kotlin" convention `StudyResourceDetailScreen` already uses for its own Topics-section gate) and flat-maps each resource's `StudyResourceTopicDao.getByStudyResourceId` rows into `[resourceName, publisher, topicName, testCount, questionCount]` string rows — one flat table, one row per (resource, topic) pair, no per-course aggregation. `data/export/CourseQuestionBankCsvExporter.kt` (`object`, matching the `PasswordHasher`/`PreferredNameResolver` single-purpose-utility shape) writes it as CSV to `context.cacheDir/exports/<sanitized course name> - Question Bank.csv` — a UTF-8 BOM is written first (`ef bb bf`), since Excel silently mojibakes Turkish characters (ç, ğ, ı, ö, ş, ü) in a BOM-less UTF-8 CSV otherwise; a small `csvField()` escapes any value containing a comma/quote/newline. The filename uses the course's raw stored name, not its Turkish display translation, matching the existing "never let a translated string overwrite/represent the underlying data" rule. `ui/common/ShareFile.kt`'s `shareCsvFile()` wraps the written file in a `content://` `Uri` (via a new `FileProvider`, `AndroidManifest.xml`'s first `<provider>` entry + `res/xml/file_paths.xml`'s `<cache-path name="exports" .../>`) and launches `Intent.ACTION_SEND` (`type = "text/csv"`) through `Intent.createChooser`. This is the app's first file-export/sharing code of any kind — no new library was needed (`FileProvider` ships in `androidx.core`, already transitively present via `core-ktx`), and it doesn't touch the offline hard constraint: a share-sheet handoff is local IPC, not network access, so no `INTERNET` permission was added. Confirmed on-device against the real Chemistry course: the share sheet correctly recognized the file as Excel-openable, and the pulled CSV had all 47 rows across the course's three real Question Bank resources (Miray Yayınları/eis Yayınları/ÜçDörtBeş) with exact counts, Turkish `Konu`/`Test Sayısı`/etc. headers (localized like every other UI string), correct BOM bytes, and correct quoting for topic names that themselves contain a comma (e.g. "Asitler, Bazlar ve Tuzlar").

The Export's counterpart, **Import**, was added right after by explicit follow-up request — a fourth `CourseDetailScreen` top-bar icon (`Icons.Filled.FileOpen`, between Export and Delete) that opens Android's document picker (`ActivityResultContracts.OpenDocument()`, `arrayOf("*/*")` — deliberately permissive since real file providers tag `.csv` under inconsistent MIME types) and re-imports the app's own export format back in, merging into the current course. `data/export/CourseQuestionBankCsvImporter.kt`'s `parse()` is a hand-written, quote-aware CSV row parser (handles embedded commas/quotes/newlines the same way the exporter escapes them, strips a leading BOM) that skips the header row and maps each remaining row to a `QuestionBankCsvRow` (resource name, publisher, topic, test count, question count) — malformed rows (too few fields, blank resource/topic name) are silently dropped rather than aborting the whole import. `CourseDetailViewModel.importQuestionBankCsv(csvContent, onResult)` merges deliberately, not destructively: a resource is matched by **(name, publisher)** rather than name alone, since two real resources in this app's own data can legitimately share a name with different publishers (confirmed against the real "TYT Kimya Soru Bankası" appearing twice under different publishers) — a match reuses the existing `StudyResource`, no match creates a new one (always `QUESTION_BANK` type, since that's the only type Export ever emits); a topic is matched by name case-insensitively within the course (same `addTopic`-style find-or-create pattern used throughout Topics); an existing (resource, topic) attachment has its counts **overwritten** by the CSV's values (by explicit request — the CSV is treated as the source of truth, e.g. for restoring a backup or bringing in edits made outside the app), while a new attachment is appended at the end of that resource's order. The result is reported back via a `QuestionBankImportOutcome` sealed type (`Imported(QuestionBankImportResult)` with counts of rows/resources/topics/attachments created vs. updated, or `EmptyOrInvalid` when nothing parsed) resolved to display text only in the Composable's result `AlertDialog` — the same "ViewModel emits a typed outcome, Composable calls `stringResource()` on it" split `ui/common/ErrorMessage.kt` already established, since a plain callback lambda isn't a composable context. Confirmed on-device with a hand-built test CSV covering all three merge paths at once (an existing resource+topic to overwrite, a new topic on an existing resource, and a brand-new resource) via the real system file picker (pushed to `/sdcard/Download/`, picked from Recents) — the result dialog and a WAL-inclusive DB pull both confirmed the exact expected counts (1 new resource, 1 new topic, 2 new attachments, 1 updated).

### Home dashboard (clock + upcoming exams) and exam-list countdowns

By explicit request ("a widget on the home page showing the time, day, and date... the number of days remaining until exams... both in a section on the home page and on the 'My Exams' page... For exams with sections... instead of 'sections,' it could display the specific sections"), `HomeScreen` and `ExamListScreen` both gained day-countdown UI, backed by shared helpers rather than duplicated math:

- `ui/common/DateFormatting.kt` gained `daysUntil(epochMillis)`/`startOfTodayMillis()` — both calendar-day-truncated (midnight-to-midnight `Calendar` math, not raw `millis / 86400000`, which would give the wrong answer depending on time-of-day) so "today" is always exactly `0` regardless of what time it currently is. `ui/common/ExamCountdown.kt`'s `daysUntilLabel(epochMillis)` (`@Composable`, since it resolves localized strings) turns that day count into "Today" / "Tomorrow" / "%d days left" / "Passed" — shared by both screens below rather than reimplemented per screen.
- **`HomeScreen`** gained a `GroupedCard` clock — time (`HH:mm`, 24-hour) + weekday/date (`EEEE, MMM d, yyyy`) — ticking once a minute via a `LaunchedEffect` loop that sleeps until the next minute boundary (`delay(60_000 - (now % 60_000))`), not every second; a study tracker doesn't need second-accurate time, and this avoids needless recomposition. Below it, an "Upcoming" `GroupedCard` (hidden entirely when there's nothing to show) lists every future-dated exam/section as its own row, **flattened into one sorted timeline** — confirmed via clarifying question over the alternative (one row per exam, showing only the nearest section for sectioned ones) — since a sectioned exam has no single date of its own, only its sections do, so treating "TYT" and "AYT" as independent upcoming events (each sorted by its own date) is more informative than collapsing them into their parent exam's row. Past-dated exams/sections are filtered out of this widget entirely (an "upcoming" list showing already-passed dates isn't useful) — `HomeViewModel.upcomingEvents` builds this from `ExamDao.getAllWithTypeByUserId` (reused as-is, already the shape `ExamListViewModel` uses) combined with the new `SectionDao.getByUserId`.

### Planner

A general-purpose agenda layered on top of the exam-prep model, by explicit request — its own `PlannerEvent` entity (schema v17), not a repurposing of anything above, so it can hold things with no exam/course relationship at all (e.g. a birthday) alongside things that do (a study session tied to a specific course/topic).

- **`PlannerEvent`** (`data/local/entity/PlannerEvent.kt`): id, nullable `userId` (FK `CASCADE`, same per-user scoping as `Exam`/`Course`), `title`, optional `notes`, `category: PlannerEventCategory` (`GENERAL`/`BIRTHDAY`/`STUDY`), `startDate` (epoch millis, start-of-day — the first/only occurrence), optional `startMinuteOfDay` (untimed/all-day when null) + `durationMinutes`, an optional recurrence (`recurrenceUnit: RecurrenceUnit?` — `DAY`/`WEEK`/`MONTH`/`YEAR` — plus `recurrenceInterval`, a comma-separated ISO-weekday `recurrenceWeekdays` string for `WEEK` only, and an optional inclusive `recurrenceEndDate`), and — `STUDY` only — nullable `courseId`/`topicId` (FK `SET_NULL`, `topicId` optional even when `courseId` is set, the same "exactly one populated" shape `StudyResource` already uses for its own dual-nullable FKs). Birthday is always implicitly yearly — `PlannerEventFormDialog` hides the recurrence controls entirely for that category rather than showing a locked-but-visible one, and forces `recurrenceUnit = YEAR`/`recurrenceInterval = 1` on save regardless of what the (hidden) fields hold. `durationMinutes` is never typed directly — `PlannerEventFormDialog` shows a required **End Time** `TimeInput` right below the **Start Time** one (both labeled, `planner_field_start_time`/`planner_field_end_time`) whenever "Set a time" is on, and `durationMinutesBetween()` derives the stored value from the two selected times (wrapping past midnight — `diff + 24*60` — if end is before start, so it's never zero or negative). This replaced an earlier free-typed "Duration (minutes)" text field that could be left blank or entered as `0` — a real on-device event ("Tarkovsky Movies Event") had silently saved that way and displayed as a degenerate "17:00 – 17:00" until re-saved through this fixed dialog; requiring an explicit end-time selection (not just a number) makes that state impossible to create going forward, by explicit request ("if there is no ending hour... user has to select it as well").
- **`PlannerEventCompletion`** (schema v17): id, `plannerEventId` (FK `CASCADE`), `occurrenceDate` (epoch millis, which specific occurrence — not the event — was marked done), `completedAt`. A unique `(plannerEventId, occurrenceDate)` index backs an idempotent toggle (`OnConflictStrategy.IGNORE` on insert, delete-by-key to un-mark) — completion is per-occurrence, so marking one Monday of a "every Monday" recurring event done doesn't affect any other Monday.
- **Recurrence math lives entirely in `ui/planner/PlannerOccurrences.kt`'s `occurrencesInRange(event, rangeStart, rangeEnd)`** — the one function every agenda view (Week/Month/Year) and the Home preview card all call. It fast-forwards mathematically to just before `rangeStart` (ceiling-division arithmetic per unit) rather than looping one step at a time from the event's anchor date, so an event created years ago still resolves instantly for a one-week window; a `MAX_CANDIDATES` backstop (10,000) guards only against a corrupt row (e.g. `recurrenceInterval` somehow 0), never hit by any realistic window. `YEAR` recurrence on a Feb 29 anchor falls back to Feb 28 in non-leap years. `java.time` is used throughout this file and its siblings (`PlannerDates.kt`, `PlannerHomeViewModel.kt`, `PlannerEventFormDialog.kt`) — **the only place in the app that does** — via `PlannerDates.kt`'s `Long.toLocalDate()`/`LocalDate.toStartOfDayMillis()` boundary functions; core library desugaring (`isCoreLibraryDesugaringEnabled = true`, `coreLibraryDesugaring(libs.desugar.jdk.libs)`) was added to `app/build.gradle.kts` specifically to make this safe on `minSdk 24` — the build change the Statistics section (above) had earlier flagged as "otherwise unneeded" and avoided by sticking to `Calendar`/`SimpleDateFormat`; Planner is what finally needed it. `PlannerOccurrences.kt`'s logic has its own unit test suite, `app/src/test/java/com/ridvan/target/ui/planner/PlannerOccurrencesTest.kt` — the app's first, since everything before this was verified on-device rather than with a test runner (recurrence math has enough edge cases — interval spacing, weekday sets, Feb 29 — to be worth a real regression net beyond on-device spot checks).
- **`PlannerHomeScreen`** (`ui/planner/`, its own drawer entry — `Icons.Filled.CalendarMonth`, `label_planner` — positioned as a standalone item directly below the collapsible "Study" group, not inside it, since a general-purpose planner isn't exam-prep-specific the way Exams/Courses/Study Resources/Topics/Statistics/Languages are) has a Week/Month/Year `SegmentedToggle` (`PlannerViewMode`) plus a prev/next period stepper. `PlannerHomeViewModel.agendaItems` merges three sources into one sealed `PlannerAgendaItem` list for whatever date range the current mode+anchor imply (`visibleRange`): `PlannerEvent` occurrences (via `occurrencesInRange`), non-sectioned exams with a date, and sections with a date — reusing `ExamDao.getAllWithTypeByUserId`/`SectionDao.getByUserId` exactly as Home's own Upcoming card does, so an exam/section shows up on both without a second query shape. Week view is one `GroupedCard` per day (`PlannerWeekAgenda.kt`); Month view is a calendar grid with a dot under any day that has items, tapping a day shows that day's agenda below the grid in the same per-day-card composable (`DayAgendaCard`, shared with Week); Year view is 12 collapsible month sections (`PlannerYearList.kt`, only the current month starts expanded — expanding all 12 by default was judged an unscannable wall of text, collapsing all would hide the one section most people open Yearly to see first). Tapping an `EventOccurrence` row opens `PlannerEventFormDialog` pre-filled for editing (Delete inside it, labeled "Delete this series" instead of "Delete this event" when the event recurs, since deleting one `PlannerEvent` row removes every occurrence, not just the tapped one); tapping an `ExamEntry`/`SectionEntry` row navigates straight to that exam's/section's own existing detail screen, the same "read-only entries jump to the real thing" precedent `StudyLinkLine` already established for a Study category event's attached course/topic.

### Notifications

By explicit request ("for tomorrow can we add a notification feature like in general with settings, preferences and working notifications?"), the app gained local reminder notifications for both Planner events and non-sectioned Exam/Section dates — the first thing in the app that runs outside the foreground UI, and the reason "local notifications/reminders" is no longer in the out-of-scope list below (still no network access of any kind — local `AlarmManager` scheduling doesn't touch the offline constraint).

- **Scope, confirmed via clarifying questions before building**: both Planner events *and* Exam/Section dates get reminders (not Planner-only); a single global lead-time preference applies to every *timed* event (not a per-event override); an untimed/all-day item (a Birthday, an untimed Planner event, or any Exam/Section date — none of which have a time-of-day field) always reminds at a fixed **9:00 AM** on the day, not on the lead-time preference; delivery uses `AlarmManager`'s exact-alarm APIs (`setExactAndAllowWhileIdle`, falling back to inexact `set()` if the user hasn't granted the exact-alarm special permission) rather than `WorkManager`, so a "15 min before" reminder actually fires within seconds of the right moment rather than drifting by minutes.
- **No new Room table or schema migration** — deliberately. Rather than persisting one row per future notification (unbounded for a recurring Planner event) or a "last notified" marker, `data/notifications/NotificationScheduler.kt`'s `reschedule(context)` recomputes the single *next* reminder moment across every source from scratch every time it's asked to, and keeps exactly one `AlarmManager` alarm armed for it — the same "derive, don't persist a redundant field" convention the rest of the app already uses for net score/blank count/etc. A reminder whose moment has already passed by the time `reschedule()` runs (app was closed through it, lead-time preference just got turned down, etc.) is simply never generated as a future candidate, so it's silently skipped rather than fired late — there is no backfill-on-relaunch behavior, by design.
- **`buildCandidates()`** fetches the signed-in user's `PlannerEvent`s (+`PlannerEventCompletion`s, so a completed occurrence is excluded — no point reminding about something already checked off), non-sectioned `Exam`s with a date, and dated `Section`s — the exact same three sources and DAOs `PlannerHomeViewModel`/`HomeViewModel`'s Upcoming card already read, so a reminder always matches what the app itself shows as "upcoming." Recurring Planner events reuse `ui/planner/PlannerOccurrences.kt`'s `occurrencesInRange()` (and `PlannerDates.kt`'s `Long.toLocalDate()`/`LocalDate.toStartOfDayMillis()` boundary helpers) directly rather than duplicating the fast-forward recurrence math — `data/notifications` is the second, and only other, place in the app that touches `java.time`, both riding on the same core-library-desugaring flag Planner already turned on. A timed candidate's reminder instant is `occurrence start − lead minutes`; an untimed/all-day candidate's is always `occurrence date @ 09:00 local`. Each candidate is looked ahead up to 400 days (comfortably past a yearly recurrence) so a single `reschedule()` call never needs to loop.
- **The "one alarm, chain-reschedule" pattern**: `reschedule()` picks the single soonest future candidate and arms one `AlarmManager` alarm for it (a fixed request code, so a second call always replaces rather than stacks); when it fires, `NotificationAlarmReceiver` calls `fireDueAndReschedule()`, which shows a notification for every candidate whose moment has now arrived (normally just one, but a shared exact moment — e.g. two events with the same lead-adjusted time — fires as a batch) and then immediately calls `reschedule()` again to arm the next one. This chain is what keeps the schedule current indefinitely without ever needing more than one live alarm or any "already notified" bookkeeping.
- **Rescheduling triggers**: `TargetApplication.onCreate()` registers a `RoomDatabase.InvalidationTracker.Observer` on the `exams`/`sections`/`planner_events`/`planner_event_completions` tables — any write to any of them (adding/editing/deleting an exam, section, or Planner event from *any* screen, or toggling a completion) calls `reschedule()` automatically, the same mechanism that already powers every Flow-backed query in the app, so no individual ViewModel (`ExamDetailViewModel`, `SectionDetailViewModel`, `PlannerHomeViewModel`, etc.) had to be touched to wire this in. Preference-only changes (`notificationsEnabled`/`notificationLeadTime`, both in `AppPreferences`, same `SharedPreferences`-backed `StateFlow` shape as `isDarkMode`/`useBlueAppIcon` — device-wide, not per-user, matching every other Settings toggle) aren't table writes, so `AppPreferences.currentUserId`'s setter and the two notification-preference setters each call `reschedule()` directly instead — the `currentUserId` hook alone covers Login/Register/Switch Account/Log Out for free, since all four already funnel through that one setter. `TargetApplication.onCreate()` also calls `reschedule()` once on every cold start (a safety net — Doze/force-stop can in principle drop a pending alarm), and `data/notifications/BootCompletedReceiver.kt` (`RECEIVE_BOOT_COMPLETED`) re-arms it after a device reboot, since `AlarmManager` alarms don't survive one.
- **Permissions**: `POST_NOTIFICATIONS` (API 33+) is requested via `rememberLauncherForActivityResult(RequestPermission())` the moment the user flips the Settings toggle on — denying it reverts the toggle back off rather than leaving an enabled-but-silently-broken state. `SCHEDULE_EXACT_ALARM` (API 31+) can't be requested through a normal runtime-permission dialog on this `targetSdk`; `SettingsScreen` instead shows a small "Exact alarms aren't allowed yet — tap to grant permission" link (only while notifications are on and the permission is missing) that opens `Settings.ACTION_REQUEST_SCHEDULE_EXACT_ALARM` — Android's own "Alarms & reminders" page for the app. The hint's visibility is rechecked via `LifecycleResumeEffect` so it disappears the moment the user grants it and returns, without needing to relaunch the app.
- **Settings UI**: a new `GroupedCard` (below Language Preference) with a Notifications label + `Switch`, a `HelpTooltip` explaining the lead-time-vs-9AM split, and — only while enabled — a 4-segment `SegmentedToggle` (`NotificationLeadTime`: `AT_TIME`/`MIN_15`/`MIN_30`/`HOUR_1`, default `MIN_15`) plus the static all-day hint and the conditional exact-alarm-permission link. `showNotification()` builds the notification text (channel name/description, "Upcoming exam"/"Upcoming exam section" titles, the generic "Reminder" fallback body for a note-less Planner event) via a throwaway `Context.createConfigurationContext()` wrapped in the user's `AppLanguage` preference — the same problem and the same fix `MainActivity.attachBaseContext()` already solved for dialogs, just needed again here because a `BroadcastReceiver` has no Activity to inherit a locale override from.
- Confirmed on real hardware end-to-end, including the exact chain-reschedule mechanics (not just the UI): granted `POST_NOTIFICATIONS` and `SCHEDULE_EXACT_ALARM` through their real system dialogs; `dumpsys alarm` showed the very first computed alarm land at exactly 16:45 (the real "Tarkovsky Movies Event"'s 17:00 start minus the default 15-minute lead); switching the lead-time preference to "At start time" live-moved that same pending alarm to 17:00; a manually-broadcast alarm fire correctly found nothing due yet and just re-armed the same 16:45 alarm untouched, proving the due-filter doesn't fire early; inserting a real throwaway Planner event 2 minutes out correctly and immediately (via the invalidation-tracker hook) moved the pending alarm to that event's exact start time, `dumpsys alarm` showed it fire at that precise second, a real system notification appeared in the shade with the correct title/time-range body, and the chain then re-armed itself back to the original 16:45/17:00 event — all without a crash (`adb logcat` clean throughout). The throwaway event was deleted afterward and the deletion was confirmed the same way the rest of this session confirms on-device data (a WAL-inclusive `.db` pull and direct `sqlite3` query, not a screenshot) — screen-based verification had to stop partway through this session once real personal notification content (an unrelated messaging app's own reply draft, already sitting in the shade before this session touched anything) became visible in a screenshot; every remaining check was done through `adb shell dumpsys`/database inspection instead, which is worth remembering as the fallback verification path any time a future session's testing risks surfacing the developer's own personal notifications on screen.

**Device alarm (a separate, second thing from the Notifications above)**: right after Notifications shipped, the user asked for something different — a "make an alarm for this event" action that hands off to the *system Clock app* to create a real, loud device alarm, not another in-app silent reminder. `ui/planner/PlannerDeviceAlarm.kt`'s `launchSetDeviceAlarmIntent(context, title, minuteOfDay, recurrenceUnit, weekdays)` fires Android's public `android.provider.AlarmClock.ACTION_SET_ALARM` intent (`EXTRA_HOUR`/`EXTRA_MINUTES`/`EXTRA_MESSAGE`, plus `EXTRA_DAYS` — an `ArrayList<Int>` of `Calendar` day constants, Sunday=1..Saturday=7 — only when `recurrenceUnit == RecurrenceUnit.WEEK`, converted from `java.time.DayOfWeek`'s ISO numbering (Monday=1..Sunday=7) via `(isoValue % 7) + 1`) and returns `false` rather than throwing if no app can handle it (mirrors `ShareFile.kt`'s "report failure as a return value" shape for this kind of external-boundary call). It takes the dialog's *live* in-progress state (not a saved `PlannerEvent`), so it works identically whether creating a new event or editing an existing one, with no Save required first.

The action lives inside `PlannerEventFormDialog`'s time section (not on every agenda row, by explicit choice) — a clickable icon+label row right after the End Time `TimeInput`, shown only while "Set a time" is on, styled like the dialog's existing "Delete this event" row but in `primary` color since it's a positive action rather than destructive. Directly under it, a caption always explains the one real limitation of Android's public alarm-clock intent: it has no concept of a specific future date, only time-of-day (+ optional weekday repeat) — so a one-time event several days out still produces an alarm that fires at the *next* occurrence of that time (i.e. today or tomorrow), not the event's actual date. Confirmed via clarifying question that the action should stay **always visible with this caption** rather than being hidden for far-future one-time events — the caption text itself swaps between a plain-time wording and a "repeating on the same days as this event" wording depending on `recurrenceUnit == WEEK`. `com.android.alarm.permission.SET_ALARM` was added to the manifest alongside the three Notifications permissions — a normal, install-time-granted permission with no runtime prompt, purely defensive for OEM Clock apps that check for it.

Confirmed on real hardware: tapping the action on a non-recurring, non-saved draft event ("Alarm test," 09:00) opened Samsung's Clock app directly (`com.sec.android.app.clockpackage`), which — unlike AOSP's DeskClock — creates and enables the alarm immediately rather than showing an edit screen first; the created alarm correctly showed "Alarm test" / 09:00 / "Mon, Sep 21" (the next occurrence of 09:00 from the actual test time of 14:30, confirming the "next occurrence, not the event's date" semantics the caption describes) with no repeat days, matching the non-recurring case. Setting the event's recurrence to Weekly with Tuesday + Thursday selected and tapping the action again produced a device alarm whose weekday indicator correctly lit up exactly Tuesday and Thursday (visually confirmed against the system Clock's own "S M T W T F S" row) — verifying the ISO→Calendar weekday conversion has no off-by-one error, which was the one genuinely fiddly part of this feature given Sunday sits at opposite ends of the two numbering schemes. The Turkish caption ("Saat uygulamanızı bu saat için bir alarmla açar...") was confirmed to render with no overflow in the dialog's fixed-width column. Both real device alarms it created during testing ("Alarm test" plain and "Alarm test" weekly) were deleted afterward via the Clock app's own multi-select UI — carefully, after this testing session hit a real mis-tap that nearly deleted one of the developer's own pre-existing real alarms (04:00/04:30 every day) instead of the test one; every deletion in this feature's testing was double-checked via `uiautomator dump`'s exact `checked=true` state before confirming, precisely because the Clock app's own list has no undo.

### Focus Timer

By explicit request, a Pomodoro-style work/break interval timer — the user's own framing was general-purpose ("employees track work and break times"), not exam-content-specific, so it's a standalone feature with only an *optional* link into the study model, not a Practice-Session variant. Deliberately kept separate from Practice Sessions/`PracticeLog` — that model tracks *questions solved*, this one tracks *time spent in a work/break rhythm*; the two are never merged, and Focus Timer sessions do not appear in the Statistics screen (which is scoped to question-count-based sources).

- **No fixed templates** — confirmed via clarifying question, the user explicitly did not want hardcoded intervals like "25/5" shipped as selectable presets. Instead, `FocusPreset` (schema v18) is a per-user reusable named pool — id, nullable `userId` (FK `CASCADE`, same scoping as `Course`/`Language`), `name`, `workMinutes`, `breakMinutes` — managed via `ui/focustimer/FocusPresetListScreen.kt`/`FocusPresetListViewModel.kt`, a direct transplant of `LanguageListScreen`'s list/add/edit/delete shape (a back-arrow `Scaffold`, reached only from `FocusTimerScreen`'s own "Focus Presets" link, not a drawer destination of its own).
- **`FocusTimerScreen`/`FocusTimerViewModel`** (`ui/focustimer/`) is the new drawer destination — a standalone item directly below Planner (`Icons.Filled.Timer`, `ShellDestination.FOCUS_TIMER`), same "general-purpose, not nested under the Study group" placement Planner already established. Idle state: a preset picker (empty state prompts creating one, no seeded default), an optional Course dropdown ("None" default) and, once a course is picked, an optional Topic dropdown (`TopicDao.getByCourseId`, reused as-is) — mirroring `StudyResource`'s "exactly one populated, topic optional even when course is set" dual-nullable shape. Running state: a live MM:SS countdown, a Work/Break phase label, a cycle counter, Pause/Resume + Stop, and the linked Course/Topic name rendered as a tappable link (`onCourseClick`/`onTopicClick`, navigating to the same `CourseDetailRoute`/`TopicDetailRoute` every other "tap through to the real thing" spot in the app uses).
- **Repeats until manually stopped** — confirmed via clarifying question, no upfront "N rounds" target. The countdown is wall-clock based (`phaseEndAt = System.currentTimeMillis() + minutes*60_000`, recomputed remaining time every 1s tick), not a naive per-tick decrement, so a brief foreground interruption still reports the correct remaining time on the next tick — the same principle `HomeScreen`'s `ClockCard` already established for its own minute-aligned tick loop, adapted to 1s cadence here. `cyclesCompleted` increments each time a **Work** phase finishes (the meaningful "how many Pomodoros" count); actual elapsed work/break time is accumulated tick-by-tick in the ViewModel (not assumed from completed-interval counts), so a session stopped mid-phase still records real partial minutes rather than 0 or a full interval.

### Statistics

The final piece of the Practice Sessions arc: a dedicated `ui/statistics/StatisticsScreen.kt`/`StatisticsViewModel.kt` (new drawer entry, `Icons.Filled.BarChart`, between Topics and Languages) that aggregates all of a user's logged sessions in one place, filterable by exam/course/topic and slicable by time period, so a student can see themselves improving rather than only ever viewing one topic's numbers in isolation. By explicit request: "feature engineer" derived metrics beyond raw sums (accuracy %, pace), and a real trend chart, not just numbers.

`PracticeLogDao.getAllForUser(userId)` (backed by a new `PracticeLogWithTopicContext` projection — `@Embedded PracticeLog` + `topicId`/`topicName`/`courseId`) fetches the user's **entire** practice-log history once, joined up through `study_resource_topics`→`topics`→`courses` and scoped by `courses.userId`. Every filter, time-window, and metric computation happens in Kotlin over that one list — deliberately not per-period SQL queries — consistent with the app's established "aggregate/filter in Kotlin over a fetched list" convention (`TopicDetailViewModel`'s totals, `TopicProgressScreen`'s aggregate line, `CourseDetailViewModel`'s CSV export all do this already). Realistic data volume here is one user's own manually-logged sessions, not a scale that needs database-side aggregation.

**Filters** cascade exactly like the original three-filter design called for: Exam ("All Exams" default) → narrows the Course dropdown to that exam's attached courses via the **existing** `ExamCourseDao.getByExamId` (no new reverse Course→Exam query needed) → Course ("All Courses") → Topic ("All Topics", enabled only once a course is picked, via existing `TopicDao.getByCourseId`). Applying a filter is a plain Kotlin `.filter` on the fetched rows' own `courseId`/`topicId` fields (and, for the exam filter, whether `courseId` is in the selected exam's attached-course-id set).

**Period**: `StatsPeriod` (`DAILY`/`WEEKLY`/`MONTHLY`/`ALL_TIME`, a 4-segment toggle styled like the existing `SettingsToggleSegment`s, default `ALL_TIME`). Bucketing/windowing uses `java.util.Calendar` (matching `DateFormatting.kt`'s existing `Date`/`SimpleDateFormat` usage — `minSdk = 24` with no core-library-desugaring configured, so `java.time` isn't safely available without an otherwise-unneeded build change). Recent-window sizes: Daily → last 14 days, Weekly → last 8 weeks, Monthly → last 6 months, All-time → bucket by month across the full history (capped at the most recent 24 buckets). Selecting a period re-windows **both** the summary numbers and the chart, not just the chart — so switching to Weekly/Monthly genuinely narrows what you're looking at, per the user's explicit ask to be able to "see improvements per weekly or even monthly."

**Derived metrics** (`StatsSummary`, computed from whatever rows are in the current filter+period window): the existing net-score formula reused as-is, plus two new ones confirmed via clarifying question — **accuracy** (`solved / (solved+unsolved) * 100`, `stat_accuracy_label`, 0 when no questions attempted) and **pace** (`durationMinutes / (solved+unsolved)` and `/ testsSolved`, `stat_pace_label`, "X.X min/question · X.X min/test").

**Trend chart**: a private `TrendBarChart` composable using Compose `Canvas` (no new dependency — confirmed no charting library exists in `app/build.gradle.kts`) draws one **stacked** bar per period bucket (solved segment + unsolved segment), so the chart doubles as a visual accuracy trend, not just a volume trend. Bucket labels render in a `Row` of `Text` underneath the canvas rather than via `drawText` (kept the canvas code simple); to avoid overcrowding, only every Nth label renders (`buckets.size / 6` step) while every bar still gets its correct width/position.

**Breakdown list** groups the current filter+period window's rows by `topicId` (the finest available granularity), each row `"<topic name> (<course name>)"` — `courseDisplayName()`-translated, matching how a course name is shown read-only everywhere else in the app — with its own tests/solved/unsolved/duration (`session_row_summary`, reused as-is), tap-through to `TopicDetailRoute` (the cross-publisher topic page — correct destination since a topic can span multiple resources/publishers).

One pre-existing (not introduced this session) minor issue was found while testing, then fixed by explicit follow-up request: `TopicDetailScreen`'s contribution list (`StudyResourceTopicDao.getByTopicId`) ordered only by `study_resources.name ASC`, with no secondary sort key — so when multiple resources share the exact same name (a known real duplicate in this app's own data — two "TYT Kimya Soru Bankası" resources, one pair even sharing the same publisher too), SQLite's unspecified tie order meant the row order wasn't guaranteed stable across recompositions. Fixed by adding `study_resources.publisher ASC, study_resources.id ASC` as secondary/tertiary sort keys — `id` alone would have been sufficient for determinism, but ordering by publisher first keeps same-named/same-publisher duplicates visually grouped rather than interleaved with the correctly-distinct-publisher rows. ### Practice Exams

By explicit request, the previously out-of-scope `PRACTICE_EXAM` `StudyResourceType` (an enum value that already existed but had no behavior behind it) was built out — but the shape went through a real redesign mid-implementation after the developer tried the first version on-device. The **first** version put a single question count directly on the `StudyResource` and modeled results as many dated "attempts" of that one exam (schema v13). After trying it, the developer clarified the real mental model: a Practice Exam `StudyResource` (e.g. "Denemeler" under Chemistry, publisher "ÜçDörtBeş") is a **container/directory** holding many individually-named exams ("Deneme 1", "Deneme 2", ...), each with its **own** question count — entered only when that specific named exam is added, not when the container itself is created. `MIGRATION_13_14` undoes the wrong `questionCount` column on `study_resources` via the standard SQLite drop-column-via-recreate pattern (create `study_resources_new` without it, `INSERT ... SELECT` the real columns across, drop and rename — matching `MIGRATION_8_9`'s existing recreate precedent, chosen specifically because real Chemistry Question Bank data lives in that table and had to survive untouched) and drops/recreates the attempt-shaped tables (`practice_exam_attempts`/`practice_exam_topic_results`, which only ever held this session's own throwaway test data) into the corrected shape: `practice_exam_entries` (`PracticeExamEntry`: id, `studyResourceId` FK cascade, `name`, `questionCount`, `correctCount`/`wrongCount`/`durationMinutes` — all default 0, since a named exam is created with just a name+count and its result filled in later) and `practice_exam_entry_topic_results` (`PracticeExamEntryTopicResult`, unchanged shape from the first version, just re-keyed to `practiceExamEntryId`). A named exam holds exactly **one** editable result, not a history of dated attempts (confirmed via clarifying question) — retaking it means overwriting its numbers, the same "tap to open a small editor" pattern as `StudyResourceTopic`'s own counts. The **blank/unanswered count (boş)** is always derived (`questionCount - correctCount - wrongCount`, `coerceAtLeast(0)`), never stored — the same "compute in Kotlin, don't persist a redundant field" convention as net score/accuracy elsewhere.

Per a second round of on-device feedback, the feature is **inline on `StudyResourceDetailScreen`**, not behind a button to a separate list screen — the developer explicitly didn't want an extra tap to see the practice exams ("i do not like to tap the button and saw the practice exams. just list them at the detail page"). When `studyResource.type == PRACTICE_EXAM`, the screen shows a "Practice Exams" section (mirroring the existing Topics section's shape exactly): a "+ Add Exam" action opens a small dialog (Name + Question Count only — correct/wrong are deliberately not asked here, only entered once the exam is actually taken), an aggregate stats line once any exams exist (`practice_exam_entries_summary`: count, total correct/wrong, accuracy %, total duration — same derivation as `CourseStudyResourceScreen`'s target/progress header), and a list of entry rows (`"<name>" / "<correct>✓ / <wrong>✗ / <blank> boş"`). Tapping a row still drills into its own screen, `ui/practiceexam/PracticeExamEntryDetailScreen.kt` (`PracticeExamEntryDetailRoute(entryId)`) — editing one entry's result plus its optional per-topic breakdown needs more room than an inline row, the same "list inline, drill in for the deep editor" split `StudyResourceDetailScreen`'s Topics section already has with `TopicProgressScreen`. That screen's Edit action opens a Correct/Wrong/Hours/Minutes dialog with correct+wrong **capped** to the entry's own `questionCount` (same live-clamping convention as `LogSessionDialog`), showing the live-computed blank count as a hint; Delete cascades the entry's topic-result rows. Below, **only when the owning `StudyResource` has a `courseId` or `languageId` set** (Topics/topic-breakdowns originally stayed Course-only everywhere in the app; both this gate and `StudyResourceDetailScreen`'s own were generalized together once Topics started supporting Languages too — see "Topics for Languages" below), a Topic Breakdown section lets you optionally attach the resource owner's topics (checklist-picker, same shape as `StudyResourceDetailScreen`'s Add Topic dialog) and edit each one's own Question Count/Correct/Wrong — the per-topic cap is against **that row's own** question count, not the overall entry's, a bug caught and fixed during on-device testing (the first pass wrongly capped against the entry's total).

**Statistics integration**: `StatisticsViewModel` gained a `StatsSource` toggle (`PRACTICE_SESSIONS`/`PRACTICE_EXAMS`, default `PRACTICE_SESSIONS` so existing behavior is unchanged) rendered as a second segmented toggle above the existing filters. Selecting Practice Exams swaps the data source to `PracticeExamEntryDao.getAllForUser`/`PracticeExamEntryTopicResultDao.getTopicAggregatesForUser` (same join-through-`study_resources`/`courses`-scoped-by-`userId` shape as the Practice Sessions source) — the Exam/Course filters still apply, the Topic filter is disabled for this source (an entry isn't inherently scoped to one topic, since its breakdown is optional and can span several), the summary/chart reuse the exact same components (just fed entries instead of logs, with "tests" now meaning "how many named exams"), and the breakdown list is replaced by a **"Topics to Work On"** ranking (`practice_exam_entry_topic_results` aggregated across all of a user's entries, sorted **ascending** by accuracy — the topics most worth reviewing float to the top), tapping through to the same `TopicDetailRoute` as everywhere else.

By the same follow-up request, the Statistics screen's **Exam filter dropdown now groups by exam type** (University Entrance Exam / High School Entrance Exam / Language Exam / Vocational Exam headers, each with its exams listed underneath, rendered via `examTypeDisplayName()`) instead of one flat list — mirroring the Courses screen's bucket grouping conceptually, though implemented as dropdown section headers rather than separate screens, since `DropdownMenu`'s content lambda is already a real composable context (no `LazyListScope`-style "compute the key outside, call `stringResource` only inside `item{}`" workaround needed here). `StatisticsViewModel.examGroups` groups the existing `ExamDao.getAllWithTypeByUserId` projection (`ExamWithType.examTypeName`) by type name, ordered against the canonical `ExamTypeDao.getAll()` seed order (University Entrance → High School Entrance → Language → Vocational) rather than first-seen order, so the grouping is stable and matches every other exam-type bucket ordering in the app.

Real on-device use of the feature surfaced one more bug, reported directly ("i enter to kimya 1 7 correct but in topics i can add 1 wrong, it is a bug"): `PracticeExamEntryDetailScreen`'s Topic Breakdown editor only capped a topic row's correct/wrong against *that row's own* question count, never against how much of the **entry's** overall correct/wrong the other topic rows already accounted for — so a topic could record a wrong answer even when the entry itself had zero wrong answers overall. By explicit follow-up request, the course/language Study Resources list (`StudyResourceListContent.kt`, shared by `CourseStudyResourceScreen`/`LanguageStudyResourceScreen`) gained a **Type filter** — a dropdown (`StudyResourceTypeFilterField`, mirroring the shape of the existing `StudyResourceTypeField` picker but with a nullable "All Types" option prepended) that narrows the rendered list to one `StudyResourceType`. ### Localization (English/Turkish)

Every user-facing string in the app lives in `res/values/strings.xml` (English, default) and `res/values-tr/strings.xml` (Turkish) — no hardcoded UI string literals remain anywhere in `ui/`. Common repeated words (Cancel/Save/Add/Delete/Name/Icon, etc.) are consolidated into shared `common_*`/`label_*` resources reused across screens rather than redefined per-dialog. **Trailing/leading spaces in a string resource are silently stripped by the XML parser unless the whole value is wrapped in double quotes** (`<string name="x">"prefix "</string>`, not `<string name="x">prefix </string>`) — bit the app once already (`home_welcome_prefix`'s space before the bolded name vanished, caught on-device) — any string a build-annotated/concatenated value depends on keeping edge whitespace needs this.

- **Free-text user data is never translated, with one deliberate exception: Course names.** Exam/topic/language/study-resource names, publishers, etc. always stay exactly as typed. Courses are different by explicit request: `ui/common/CourseNameDisplay.kt`'s `courseDisplayName(name: String): String` is a `@Composable` lookup, the same display-only-at-render-time pattern as `examTypeDisplayName()` — a fixed set of common subjects ("Geometry", "Biology", "Chemistry", etc.) translate for display (e.g. "Geometri", "Biyoloji", "Kimya"); any course name outside that list (a custom name, or "German A1"/"German A2"-style language-level course names that exist as leftover pre-Language-table data) just shows as typed, same as any other free text. Applied everywhere a course name is rendered read-only (list rows, checklists, screen/dialog titles, delete-confirmation messages) — **but deliberately not** to `CourseDetailScreen`'s `CourseEditDialog` `initialName` (the field you actually edit and save): translating that would mean saving the edit dialog without touching the name field silently overwrites the real English name with its Turkish display text, corrupting the underlying data. The drawer/menu word for the Courses feature itself was also renamed in Turkish from "Kurslar" to "Dersler" ("kurs" reads as an external training course, not an academic subject) — this only touched the `values-tr/strings.xml` chrome strings (`label_courses`, `dialog_add_course_title`, etc.), not the English default wording or any code/route/table naming.
- **`ExamType.name`/`LANGUAGE_EXAM_TYPE_NAME` stays English in the database and in all comparisons** — these are seeded DB rows (see `ExamTypeDao` above), not compile-time resources. `ui/common/ExamTypeDisplay.kt`'s `examTypeDisplayName(name: String): String` is a `@Composable` lookup (`when (name) { "University Entrance Exam" -> stringResource(...), ... }`) called only at the point of *display* — every place `examType.name`/`examTypeName` is rendered to the user wraps it in this; nothing ever compares against a translated value.
- **`ui/common/CourseIcons.kt`'s `CourseIconOption` stores a `@StringRes labelRes: Int`, not a raw `String`** — icon content descriptions need `stringResource()`, which requires a Composable context, but `CourseIcons.options` is a plain top-level `val` list; `CourseIconPicker` resolves `stringResource(option.labelRes)` at the point of use instead.
- **ViewModel-originated error messages** (login/register/profile-edit/switch-account validation) can't call `stringResource()` directly (`AndroidViewModel` isn't a Composable context) — they're modeled as `ui/common/ErrorMessage.kt`'s `ErrorMessage` enum (`INVALID_USERNAME_PASSWORD`, `USERNAME_TAKEN`, etc.), exposed as `StateFlow<ErrorMessage?>` from each ViewModel, and resolved to display text via `ErrorMessage.text()` (a `@Composable` extension) only in the Screen.
- **Category/type group-header labels vs. single-value labels use different fallback text for the unset case** — `ui/common/CourseCategoryLabel.kt` has two separate composables for this reason: `courseCategoryGroupLabel()` (null → "Uncategorized", used for the Quantitative/Verbal/Uncategorized group headers in `CourseListByTypeScreen`/`ExamDetailScreen`/`SectionDetailScreen`) and `courseCategoryValueLabel()` (null → "Not set", used for a single course's own category value in `CourseDetailScreen`) — conflating them into one function would show the wrong fallback word in one of the two places.
- **A composable that groups a `LazyColumn`'s items by category (or any enum) must NOT itself be `@Composable`** — `LazyListScope`'s builder body (the lambda passed to `LazyColumn { ... }`) is not a composable context, so calling `stringResource()`-based label functions there to compute group keys fails to compile. The fix used throughout (`ExamDetailScreen.examCourseGroups`, `SectionDetailScreen.sectionCourseGroups`, `CourseListByTypeScreen.courseGroups`): group by the raw enum/nullable key (e.g. `CourseCategory?`), keep the `mutableStateMapOf` expand-state keyed by that same raw enum (not by the translated display string, which would also be locale-dependent and require re-deriving the label a second time outside the composable `item {}` block just to read the map), and only call the label composable *inside* the `item { }` block where a real composable context exists.
- **Switching languages requires `Activity.recreate()`, not just a Compose-level override** — the first implementation tried wrapping `LocalContext` via `CompositionLocalProvider` in `MainActivity`'s `setContent`, which correctly re-localized ordinary screen content but silently left every `AlertDialog`/`DropdownMenu`/`DatePickerDialog` body and button text in the OS's real locale (confirmed on-device: a dialog's title — resolved in the caller's composition, before entering the dialog — translated correctly, while the exact same dialog's "Name"/"Icon"/"Cancel"/"Save" — resolved *inside* the dialog's own composable slots — did not). `Popup`/`Dialog` create their own Android `Window` and re-derive `LocalContext` from the real Activity context there, bypassing any ambient CompositionLocal override made further up the tree. The working fix: `MainActivity.attachBaseContext()` wraps the real base `Context` in a locale-adjusted `Configuration` (reading the persisted preference via a throwaway `AppPreferences(newBase)`), and `SettingsScreen` calls `LocalContext.current.findActivity()?.recreate()` (`ui/common/FindActivity.kt`) right after `viewModel.setAppLanguage(...)`. `recreate()` behaves like a configuration-change relaunch (same mechanism `AppCompatDelegate.setApplicationLocales()` uses internally) — confirmed on-device that it preserves navigation position, scroll/dialog state, and other Settings toggles (Dark mode, App Icon) across the switch, both directions.
- `AppPreferences.appLanguage: StateFlow<AppLanguage>` (`ENGLISH`/`TURKISH`) follows the same persisted-preference shape as `isDarkMode`/`useBlueAppIcon`, defaulting to Turkish only if the *system* locale is already Turkish at first launch, English otherwise. Setting it also calls `Locale.setDefault(...)` so `ui/common/DateFormatting.kt`'s `SimpleDateFormat("MMM d, yyyy", Locale.getDefault())` picks up correctly localized month names with no changes of its own needed. Settings shows this as an English/Turkish segmented toggle, the third reuse of the `PreferredNameSelector`/App-Icon segmented-toggle visual pattern.

### Interface redesign (in progress)

By explicit request ("everything feels boxy... let's make it a bit more rounded... an interactive experience"), the app is partway through a visual/interaction overhaul, planned in phases so nothing already working regresses. Two phases are done and pushed:

**Theme/shapes**: `ui/theme/Theme.kt`'s `TargetTheme` previously passed no `Shapes()` to `MaterialTheme(...)` at all, so every component used stock Material3 defaults (extraSmall 4/small 8/medium 12/large 16/extraLarge 28dp). A custom `AppShapes` (6/10/14/20/24dp respectively) is now passed — a "subtle/modern" bump, not a "bubbly" one, confirmed via clarifying question. `Button` is unaffected either way (Material3 renders it stadium-shaped regardless of the `Shapes()` scale) — the "boxy" feeling was actually coming from the complete absence of any `Card`/`Surface` grouping, not from button corners; color scheme (`pinnedColorScheme`) and typography were deliberately left out of scope.

**Drawer active-destination highlighting**: `AppShell.kt`'s `NavigationDrawerItem`s all hardcoded `selected = false` — the current destination was never actually highlighted. `AppShell` gained a `ShellDestination` enum (`HOME`/`EXAMS`/`COURSES`/`STUDY_RESOURCES`/`TOPICS`/`STATISTICS`/`LANGUAGES`/`HELP`/`OTHER`) and a `currentDestination` param (default `OTHER`, so old call sites still compile); all 10 `AppShell(...)` call sites now pass the correct value (`UserEditScreen`/`SettingsScreen` stay `OTHER` since neither has its own drawer row — they're reached via the overflow menu). Confirmed on-device across Home/Exams/Study Resources: the previously-active row's rounded pill highlight correctly moves to whichever destination is actually open.

**Shared components**, replacing patterns that used to be hand-copied per screen:

Confirmed on-device: Settings' App Icon/Language toggles, the Preferred Name toggle (dimmed state included), and Course Detail's Category toggle all render and animate identically to before.

**Important gotcha, caught while verifying this on-device rather than by inspection**: `ListItem`'s default `containerColor` is opaque, so any `ListItem`-based row placed inside a `GroupedCard` fully **hides** the card's own tonal background wherever that row sits — only a plain `Row` (no `ListItem`, e.g. a group header) shows the intended tint. The on-device screenshot looked plausible at a glance (all one shade of near-black), and only direct pixel sampling (`System.Drawing.Bitmap.GetPixel()`, the same trick already used for `BannerColor` — see App Color Preference above) caught that a row's pixels were *identical* to the plain screen background, not just subtly different. Fixed by giving every `GroupedCard`-hosted `ListItem` row (`CourseRow`, `LanguageCourseRow`) an explicit `colors = ListItemDefaults.colors(containerColor = Color.Transparent)`. **Any future `GroupedCard` rollout that hosts `ListItem` rows needs this same fix** — it's easy to add a new card wrap, see a plausible-looking screenshot, and miss that the row backgrounds are silently opaque.

`GroupedCard` itself now applies `Modifier.animateContentSize()` to its inner `Column`, so **every** adopter's expand/collapse animates smoothly for free — no per-call-site work needed, and this retroactively benefited the `CourseListByTypeScreen`/`LanguageExamCoursesScreen` cards too. **`ExamDetailScreen`/`SectionDetailScreen`** now wrap their Courses/Sections lists (and, for `SectionDetailScreen`, its own Quantitative/Verbal/Uncategorized groups) in `GroupedCard` the same way, including the same `ListItemDefaults.colors(containerColor = Color.Transparent)` fix on every row (`CourseRow`, `SectionRow`, `AssignedCourseRow`). Confirmed on-device against the real YKS exam: the sectioned exam's Courses card correctly shows header-only (no chevron/list, per the existing `hasSections` gating), the Sections card expands smoothly to TYT/AYT, and TYT's own Quantitative group expands to its real Biology/Chemistry/Geometry/Mathematics/Physics courses with correct tint and working tap-through.

Two non-obvious bugs were caught and fixed before this was considered working, both worth remembering for any future manually-built (non-`LazyColumn`) reorderable list in this app: (1) the per-row `TopicRow` calls inside `orderedIds.forEach { ... }` **must** be wrapped in `key(id) { ... }` — without it, Compose reuses each child slot by *position* rather than by topic identity, so the instant a drag causes a swap (the dragged row's index changes), the row's `pointerInput(id)`-keyed gesture coroutine gets cancelled mid-drag (a different `id` now occupies that slot), silently ending the drag without ever calling `onDragEnd`/persisting anything — this produces no crash and no visible error, it just quietly does nothing, so it's easy to mistake for "the gesture didn't fire" rather than "the gesture fired and then got killed." (2) the drag handle's gesture cannot be built on the stock `detectDragGesturesAfterLongPress` when it lives inside a `Modifier.verticalScroll` ancestor (which the whole `StudyResourceDetailScreen` body is, per the earlier scroll fix): that function doesn't consume pointer input during its long-press wait, so the ancestor `verticalScroll` — watching the same unconsumed movement — can win the gesture race and scroll the whole page instead of starting the drag (this reproduced reliably via `adb shell input draganddrop`, which we adopted for testing this specific gesture shape since a plain `input swipe` moves immediately and never gives a long-press detector time to arm). The fix was a small hand-written replacement, `detectDragHandleGesture` (private, same file): it consumes the initial `down` **immediately**, keeps consuming every pointer move during the long-press wait (`withTimeoutOrNull(viewConfiguration.longPressTimeoutMillis)`), and only then starts the real drag — so the ancestor scrollable never sees an unconsumed movement to react to, regardless of what the finger does before the hold completes.
