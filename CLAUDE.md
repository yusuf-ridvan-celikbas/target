# Target — Offline Exam Prep Tracker

## What this app is

A personal, fully offline Android app for organizing exam study materials and tracking study progress. Not tied to any specific exam — the user defines whatever exam(s) they're preparing for, then organizes materials underneath. It's now genuinely multi-account (see below) — "personal" describes the deployment (one phone, not distributed), not a single-user data model.

**The data model was fully reset once already** (see git history around "Full reset" for what came before — nested Topics, Question Banks, Practice Exams, Lecture Notes, Test Attempts, pace estimation). None of that survived the reset; don't resurrect ideas from it without the user asking again. What's described below is the current, second-generation model, now with accounts layered on top.

### Accounts

Real multi-account auth, not a single-profile gate — `Register` can create additional accounts at any time; `Login` looks up by username. `User`: firstName, middleName (optional), lastName, username (unique), email (optional), passwordHash/passwordSalt (`data/PasswordHasher.kt` — salted SHA-256 via `SecureRandom`/`MessageDigest`, no new dependency; passwords are never stored or compared in plaintext), preferredName + preferredNameSource.

**Preferred name** is chosen via a toggle (First / Middle) plus three mutually-exclusive checkboxes (Last Name / Username / Other — "Other" reveals a free-text field), not typed directly — `ui/common/PreferredNameSelector.kt`, shared between Register and Edit Profile. The choice **stays live**: `User.preferredNameSource` is stored, and `data/PreferredNameResolver.kt`'s `resolvePreferredName()` recomputes the stored `preferredName` string from the current source field every time the profile is saved — so editing First Name later automatically updates Preferred Name too, if that's the active source. This is the one place in the app where a value is deliberately kept in sync via recomputation-on-save rather than either a live read-time join or a frozen one-time value.

Session persistence and the light/dark theme preference both live in `data/local/AppPreferences.kt` — a plain `SharedPreferences` wrapper (deliberately not DataStore, no new dependency needed for two small values). `currentUserId` is still read once per ViewModel at construction, not observed reactively — Log Out and Switch Account (see Navigation shell below) both clear/replace it and then force a full back-stack reset (`popUpTo(0)` to `LoginRoute`/`HomeRoute`) rather than relying on any ViewModel noticing the change mid-process, so the "read once" assumption still holds; there just wasn't a codepath that changed it before. `isDarkMode` **is** a `StateFlow`, since `MainActivity` needs to react immediately when Settings toggles it.

`Exam` and `Course` carry a nullable `userId` (FK, cascade) — nullable because real pre-auth exam data already existed on-device with no owner when accounts were added; those rows just don't appear once list queries filter by the logged-in user, rather than being destroyed. Every exam/course query and insert must be scoped by `AppPreferences.currentUserId` — there is no global, cross-account exam or course data (unlike `ExamType`, which stays a shared/seeded lookup table, not per-user).

### Exam data (unchanged in shape since the last update, now user-scoped)

Hierarchy: **Exam → (optional) Section → Courses**, plus a per-user **Course** pool, a per-user **Language** pool, and a shared, seeded **ExamType** list.

- **ExamType**: a real, seeded table (not an enum) — currently "University Entrance Exam", "High School Entrance Exam", "Language Exam", "Vocational Exam". Seeded idempotently on every app start (`ExamTypeDao.seedDefaultsIfEmpty()`, called from `TargetApplication.onCreate()`) rather than via `RoomDatabase.Callback.onCreate()` — that callback does **not** reliably fire when the schema is created via a destructive-fallback recreation rather than a genuine first-run (confirmed on-device). Managing this list (add/delete/rename by the user) is an explicitly deferred next step — don't build that screen unless asked. Shared across all accounts, not per-user. `ExamTypeDao.kt` exports `LANGUAGE_EXAM_TYPE_NAME` (= "Language Exam") as the one place that magic string lives — everywhere else that needs to know "is this exam a language exam" compares against that constant rather than a re-typed literal.
- **Exam**: name, `examTypeId` (FK), `userId` (FK, nullable — see Accounts), `hasSections: Boolean` (decided at creation, not editable afterward — toggling it later raises unresolved questions about what happens to existing sections/courses), `examDate` (meaningful only when `!hasSections`), optional `studyStartDate`, optional `languageId` (FK to Language, `SET_NULL` on delete — meaningful only when the exam's type is Language Exam; see Language below).
- **Language**: per-user, reusable, free-text name (e.g. "German") — same shape as `Course` minus icons (no icon picker for languages, unlike courses). Has its own full CRUD screen (`ui/languagelist/`, reached from Home's drawer, right after Courses) mirroring `ui/courselist/`'s list/add/edit/delete pattern. `AddOrEditExamDialog` (`ui/common/ExamFormDialog.kt`) shows a Language combobox *only* when the selected exam type's name equals `LANGUAGE_EXAM_TYPE_NAME` — it's not shown for any other exam type, and the dialog nulls out the selection on save if the type gets changed away from Language Exam. The chosen language isn't just stored silently: it also surfaces in `ExamListScreen`'s row subtitle (`examType · language · date`) and `ExamDetailScreen`'s summary (`Language: X`), the same way `examDate` already does, so picking one has visible confirmation after saving. Because deleting a Language `SET_NULL`s any exam's `languageId` that pointed to it, a Language Exam can end up with `languageId == null` two ways (never set, or set-then-deleted) — both render as an explicit "No language set" in the row/summary rather than silently omitting the line, so a Language Exam always shows *some* language state. Non-Language-Exam types never show the line at all, set or not.
- **Course**: per-user, reusable, free-text name (e.g. "Chemistry"), plus an optional `icon` (nullable `String` key, e.g. `"functions"`, `"science"`), a nullable `examTypeId` (FK to `ExamType`, `SET_NULL` on delete) — a course belongs to exactly one exam type (e.g. "Math" only ever lives under University Entrance Exam), fixed at creation but **reassignable later from `CourseDetailScreen`'s edit dialog** (see below) — unlike `Exam.hasSections`, this one deliberately isn't a "decided once" field — and a nullable `category: CourseCategory?` (`QUANTITATIVE`/`VERBAL`, `data/local/entity/CourseCategory.kt`), for University Entrance/High School Entrance/Vocational courses only (Language Exam never has `Course` rows at all — see below). The exam-level "Add course" dialog (`ExamDetailScreen`) shows the user's not-yet-attached courses as a **multi-select checklist** (`ExamDetailViewModel.availableCoursesToAdd`, checked ones added together via `addExistingCourses`) alongside a text field for creating a new course inline (create-if-missing, case-insensitive name match) — both are now scoped to the exam's own `examTypeId`, not the user's whole course pool, so a Vocational exam can never pick up a University-tagged course. It used to be blind free-text entry only — an already-created course had no visible way to be picked, only re-typed exactly — fixed after being reported as a bug. A course created inline this way (or via the section picker) gets no icon *and no category* at creation — both are only assignable from `CourseDetailScreen`'s edit dialog, not speculatively exposed in every place a course can be created. The category field is a 3-segment toggle (Unset / Quantitative / Verbal, private `CourseCategoryField`/`CategoryToggleSegment` in `CourseDetailScreen.kt`) — the third deliberate reuse of the `PreferredNameSelector`/Settings-app-icon segmented-toggle visual shape, each still its own private copy rather than a shared composable, matching how the app has handled that pattern twice before. `CourseListByTypeScreen`, `ExamDetailScreen`'s Courses pool, and `SectionDetailScreen`'s assigned-courses list all group courses into **Quantitative / Verbal / Uncategorized** sections (in that order, a group only rendered when non-empty) instead of one flat list — added after the flat list was reported as looking "crowded," then extended to sections by explicit request (initially scoped out — see `SectionCourseWithCourse` note below). Each group has its own collapsible header (chevron, default closed, same `KeyboardArrowDown`/`KeyboardArrowUp` pattern as the Courses/Sections sections below) — a `*GroupHeader` composable, one private copy per screen (`courseGroups()`/`CourseGroupHeader` in `CourseListByTypeScreen.kt`, `examCourseGroups()`/`CourseGroupHeader` in `ExamDetailScreen.kt`, `sectionCourseGroups()`/`SectionCourseGroupHeader` in `SectionDetailScreen.kt`), each over its own screen's `Course.category` / join projection's `courseCategory` field. `SectionCourseDao`'s join query and `SectionCourseWithCourse` gained `courseCategory` the same way `ExamCourseWithCourse` did, once the grouping was extended there too.
- **Courses screen, restructured by exam type**: `CourseListScreen` (`ui/courselist/`, still the drawer's "Courses" destination) is no longer a flat CRUD list — it's a menu of one row per `ExamType` (`"${examType.name} Courses"`), read straight from the seeded `ExamType` table so the order always matches (University Entrance, High School Entrance, Language, Vocational). Tapping a non-Language-Exam row drills into `CourseListByTypeScreen`/`CourseListByTypeViewModel` (`CourseListByTypeRoute(examTypeId)`) — a back-arrow `Scaffold` (not `AppShell`, matching the `ExamDetailScreen`/`SectionDetailScreen` drill-down exception) listing courses (name+icon only, no inline actions) with an "Add course" FAB (name+icon, `examTypeId` fixed to that bucket, via `CourseDao.getByUserIdAndExamTypeId`). Tapping a course row navigates to `CourseDetailScreen` (see below), not straight to Study Resources.
- **CourseDetailScreen / LanguageDetailScreen** (`ui/coursedetail/`, `ui/languagedetail/`): the landing page for a specific course or language, mirroring `ExamDetailScreen`'s shape — a back-arrow `Scaffold` with Edit and Delete icons in the top bar, plus a prominent **Study Resources** button that navigates on to the actual study-resource list. `CourseDetailScreen`'s edit dialog covers name, icon, *and* exam type (a `DropdownMenu`, same pattern as `ExamFormDialog`'s `ExamTypeField`) — the dropdown deliberately excludes the Language Exam type, since a `Course` row tagged with it would be unreachable from any Courses/Study Resources bucket (Language Exam Courses lists `Language` rows, not `Course` rows). `LanguageDetailScreen`'s edit dialog is name-only. Both screens own all editing/deleting for their entity now — the list screens that lead here (`CourseListByTypeScreen`, `LanguageExamCoursesScreen`, `LanguageListScreen`) only render name(+icon) and navigate on tap, with no inline edit/delete affordances of their own, applied uniformly across every entry point.
- **Language Exam Courses is its own screen, not an alias for the Languages drawer screen**: tapping "Language Exam Courses" navigates to `LanguageExamCoursesScreen` (`ui/languagelist/LanguageExamCoursesRoute`) — a back-arrow `Scaffold` drill-down (mirroring `CourseListByTypeScreen`'s chrome) that reuses the existing `LanguageListViewModel` as-is (it has no route/nav dependency, so the same add-language logic runs under a second, independent navigation entry) rather than navigating into the drawer's `LanguageListRoute`. This was a deliberate correction: the two screens show the same underlying `Language` data and both let you drill into a language's detail/Study Resources, but they are different back-stack destinations reached from different parents (Courses vs. the drawer) — exactly like `CourseListByTypeScreen` is never the literal `CourseListScreen`. The drawer's own "Languages" item (`LanguageListScreen`) stays as a separate, always-available shortcut to the same data, by the user's explicit choice — it now also routes a tapped row to `LanguageDetailScreen` rather than editing inline, for consistency with every other entry point.
- **Study Resources** (named "Study Sources" until renamed throughout by explicit request — see `MIGRATION_8_9` below): a per-course/per-language resource list, and also its own top-level drawer destination (`StudyResourceHomeRoute`/`StudyResourceHomeScreen` in `ui/studyresource/`, positioned in the drawer between Courses and Languages). `StudyResourceHomeScreen` reuses `CourseListViewModel` and renders the identical four-exam-type-bucket menu as `CourseListScreen`, but tapping a bucket routes to its **own** drill-down destinations — `StudyResourceCourseListByTypeRoute(examTypeId)` and `StudyResourceLanguageExamCoursesRoute` — not the Courses flow's `CourseListByTypeRoute`/`LanguageExamCoursesRoute`, even though all four routes render the exact same `CourseListByTypeScreen`/`LanguageExamCoursesScreen` composables (and, for the course case, the same route-agnostic `CourseListByTypeViewModel`, which reads `examTypeId` by argument name via `savedStateHandle.get<Long>("examTypeId")` rather than a route-typed `toRoute<>()`, precisely so it can back both routes; `LanguageExamCoursesScreen` already had no route dependency at all, reusing `LanguageListViewModel` as-is). The reason for the split: tapping a course/language from the *Courses* flow still goes to `CourseDetailRoute`/`LanguageDetailRoute` (edit/delete/exam-type live there), but tapping one from the *Study Resources* flow must skip Detail entirely and land directly on `CourseStudyResourceRoute`/`LanguageStudyResourceRoute` — Study Resources is meant as a shortcut straight to the study-resource list, not a second path into Detail. This was originally built wrong (Study Resources aliased the Courses routes, so it always detoured through Detail first) and was corrected by giving the two entry points separate routes, per the standing "separate parents into the same data need separate routes" rule already applied to `LanguageExamCoursesRoute` vs `LanguageListRoute`. `StudyResource`: id, `name`, nullable `courseId` and nullable `languageId` (exactly one populated per row, `CASCADE` on delete of the owner), nullable `type: StudyResourceType?` (`QUESTION_BANK`/`LECTURE_TEXTBOOK`/`PRACTICE_EXAM`/`LECTURE_NOTES` — the deferred "resource types will be specified later" finally landed; nullable in the schema so pre-existing resources read as "Not set," but the Add dialog requires picking one before Save enables), and nullable `publisher: String?` (optional, collected but never required). One shared presentational composable, `ui/studyresource/StudyResourceListContent.kt`, backs the two terminal screens/ViewModels — `CourseStudyResourceScreen`/`CourseStudyResourceViewModel` (`CourseStudyResourceRoute(courseId)`) and `LanguageStudyResourceScreen`/`LanguageStudyResourceViewModel` (`LanguageStudyResourceRoute(languageId)`) — both back-arrow `Scaffold`s, titled with the owning course/language's name, reached via either their respective Detail screen's Study Resources button (Courses flow, and the Languages drawer shortcut) or directly from the Study Resources drill-down (Study Resources flow). Its Add dialog (`StudyResourceFormDialog`, also in `StudyResourceListContent.kt`) shows the owning course/language name **read-only** ("Subject: Geometry" — already auto-attached via `courseId`/`languageId`, this just surfaces it rather than asking the user to re-pick it), plus Name, a required `StudyResourceTypeField` dropdown (same `ExamTypeField`-style Box+DropdownMenu pattern used throughout the app), and an optional Publisher field. Tapping any resource row navigates to `ui/studyresourcedetail/StudyResourceDetailScreen.kt` (`StudyResourceDetailRoute(studyResourceId)`) — a back-arrow `Scaffold` owning Edit/Delete (Name/Type/Publisher all editable there; Subject is not, same "fixed at creation" precedent as other identity-defining FKs), mirroring the Course/Language Detail pattern applied uniformly across the app — so the list rows themselves carry no inline edit/delete anymore, just name + a type subtitle.
- **Topics**: per-course, reusable within that course, tracking how many tests/questions a Question Bank study resource covers for each topic — and, since multiple Question Banks (different publishers) can attach to the same topic, how many exist for that topic in total across publishers. `Topic` (`data/local/entity/Topic.kt`): id, name, `courseId` (FK, non-null, `CASCADE` — unlike `StudyResource`'s dual-nullable courseId/languageId, a Topic has exactly one parent, so it follows `Section.examId`'s simpler non-null-FK shape). Topics are **Course-only** — Language-based Question Banks never show a Topics section, by deliberate scope decision, not an oversight. The join entity `StudyResourceTopic` (`data/local/entity/StudyResourceTopic.kt`) carries the actual counts, one row per (question bank, topic) pair: `studyResourceId`/`topicId` (both FK `CASCADE`, unique compound index), `testCount`/`questionCount: Int` (default 0) — mirrors `ExamCourse`/`SectionCourse`'s join-table shape exactly. `TopicDao.getTopicTotalsByCourseId(courseId)` is the cross-publisher aggregate query (`LEFT JOIN` + `SUM` + `COALESCE`, so a topic with no attachments still shows 0/0 rather than disappearing); `StudyResourceTopicDao.getByTopicId(topicId)` is the per-publisher breakdown query, `getByStudyResourceId(studyResourceId)` lists topics attached to one resource.

  On `StudyResourceDetailScreen`, when `studyResource.type == QUESTION_BANK && studyResource.courseId != null`, a "Topics" section appears: an "Add Topic" checklist-picker-with-create-inline dialog (a direct transplant of `ExamDetailScreen`'s `AddCourseDialog`/`addCourse`/`addExistingCourses` pattern, scoped to the resource's `courseId` instead of `(userId, examTypeId)`) attaches topics at 0/0, then each attached-topic row is tappable to open an "Edit counts" dialog (Test Count, Question Count — **the app's first numeric input fields**: string-backed state, `onValueChange` filtered to `input.all(Char::isDigit)`, `KeyboardOptions(keyboardType = KeyboardType.Number)`, parsed with `.toIntOrNull() ?: 0` only at Save — treat this as the template for any future numeric field) with a "Remove topic from this resource" action inside the dialog rather than a trailing row icon (unlike `CourseRow`'s inline delete) — the row carries editable data, so "tap to open a small editor" fits better than a bare glance-and-remove list.

  A new **Topics** button on `CourseDetailScreen` (next to Study Resources) leads to `ui/topiclist/TopicListScreen.kt` (`TopicListRoute(courseId)`) — full CRUD, mirroring Course/Language: FAB creates a topic directly (find-or-create, case-insensitive), each row shows the topic name plus its cross-publisher totals as a subtitle, tap navigates to `ui/topicdetail/TopicDetailScreen.kt` (`TopicDetailRoute(topicId)`) — Edit (rename) / Delete in the top bar (Delete cascades `StudyResourceTopic` rows via FK, confirmed on-device), and a body showing the prominent aggregate total above a per-resource breakdown list (`"<resource name> — <publisher or \"No publisher\">"` + that resource's own counts) — **this breakdown is the feature's actual payoff**, answering "how many tests/questions exist for this topic across different publishers." Each breakdown row taps through to `StudyResourceDetailRoute`, so you can jump from a topic straight into any contributing publisher's question bank.
- **Course icons**: `ui/common/CourseIcons.kt` is a curated, fixed list (~17) of `material-icons-extended` `ImageVector`s keyed by string (Functions, Science, Biotech, MenuBook, Language, Palette, Add, etc.) — added specifically because `material-icons-core` (already a dependency) only has ~48 generic action icons, nothing subject-appropriate. `CourseIcons.iconFor(key)` resolves a nullable key to an icon, falling back to a default (`MenuBook`) when unset — this is the one place in the app an icon is chosen from a fixed palette rather than free text. `ui/common/CourseIconPicker.kt` has the picker grid (`CourseIconPicker`, used in the Courses add/edit dialog) and the small rendering helper (`CourseIconAvatar`, used everywhere a course is listed: Courses screen, `ExamDetailScreen`'s course pool and add-course checklist, `SectionDetailScreen`'s assigned/available course lists) — every one of those reads `Course.icon` / the `courseIcon` column added to the `ExamCourseWithCourse`/`SectionCourseWithCourse` join projections, so a course's icon looks the same wherever it's referenced, matching how course *names* already worked.
- **ExamCourse**: join table — an exam's own course pool. Always present regardless of `hasSections`, because sections pick their courses *from* this pool.
- **Section**: only exists when `Exam.hasSections`. Name + own `date` (a sectioned exam's "exam date" is really N section dates, not one field).
- **SectionCourse**: join table — a section's subset of its parent exam's course pool. The add-course-to-section UI is a **checklist picker** over `ExamCourseDao.getByExamId(exam.id)` minus what's already assigned, not create-if-missing (unlike the exam-level course pool) — a section can't have a course the exam doesn't already have.

`ExamDetailScreen`'s Courses and Sections lists are each collapsible, defaulting to **closed** — reported as looking "crowded" once an exam had more than a couple of courses. `SectionHeader` (private composable in `ExamDetailScreen.kt`) takes optional `expanded`/`onToggleExpand` params and renders a `KeyboardArrowDown`/`KeyboardArrowUp` chevron next to "+ Add" when supplied; the two lists track independent `coursesExpanded`/`sectionsExpanded` `remember { mutableStateOf(false) }` state and only compose their `items(...)` when expanded. Not persisted — collapses again on next screen visit, by design (no reported need yet to remember the open/closed state across navigation). The **Courses section itself is hidden entirely on Language Exam type exams** (computed via `isLanguageExam`, hoisted above the `LazyColumn` in `ExamDetailScreen`) — a Language Exam has no course pool, just its single `languageId` field (already shown/editable elsewhere), so the course-oriented "Add" flow doesn't apply there; this was reported as a bug ("can't add an existing language course to Goethe A2") before being traced to the real issue — the Courses section shouldn't have been showing on Language Exams at all. Tapping a course row in this pool navigates to `CourseDetailRoute(courseId)` via `onCourseClick` (added to `ExamDetailScreen`'s signature and wired in `TargetNavHost`) — this was missing entirely until reported as a bug (the row had a remove button but no click handler). The Language Exam analogue: `ExamSummary`'s "Language: X" line is clickable (`Modifier.clickable`, only when a language is actually set — "No language set" stays inert) and navigates to `LanguageDetailRoute(languageId)` via a third `onLanguageClick` param on `ExamDetailScreen`, giving a Language Exam the same "tap through to the thing's own detail/Study-Resources page" behavior that courses already have on other exam types. The clickable affordance wasn't discoverable as plain text, so just the language name (not the "Language: " label) is styled as a link — blue + underlined — via `buildAnnotatedString`/`SpanStyle(color = MaterialTheme.colorScheme.primary, textDecoration = TextDecoration.Underline)`, the second place in the app a single string mixes styles inline (the first being `HomeScreen`'s bolded preferred name).

The exam-level Courses list is also hidden — differently from the Language Exam case — **when the exam has sections**: the "Courses" header and its "+ Add" button still render (that's still how a course gets attached to the exam's pool that sections pick from — see `ExamCourse`/`SectionCourse` above), but the collapse chevron and the actual list of attached courses don't, since a sectioned exam's courses are meant to be seen under their section, not duplicated at the top level too. `SectionDetailScreen`'s course rows (`AssignedCourseRow`) got the same "tappable → `CourseDetailRoute`" fix as `ExamDetailScreen`'s pool did, closing the same gap (a remove button with no click handler) — so Section → Course Detail → Study Resources is now a complete chain, matching Exam → Course Detail → Study Resources for non-sectioned exams.

### App icon

Two selectable launcher icons — `ic_launcher`/`ic_launcher_round` (white/default) and `ic_launcher_blue`/`ic_launcher_blue_round` (blue) — each an adaptive icon (foreground/background XML pair in `drawable`/`drawable-xxxhdpi`, plus legacy raster fallbacks at every mipmap density). Both were generated from flat-background design PNGs (developer's desktop `target-app-designs` folder) by chroma-keying the background color to transparent for the foreground layer — there's no Android Studio Image Asset step in this workflow, so any future icon variant needs the same treatment (sample the actual flat background pixel, not a corner pixel, which can be an anti-aliasing outlier). Switching icons is done via two `<activity-alias>` entries in the manifest (`AppIconDefault`, `AppIconBlue`, both `targetActivity=".MainActivity"`), toggled at runtime through `PackageManager.setComponentEnabledSetting(..., DONT_KILL_APP)` from `SettingsViewModel.setUseBlueAppIcon()` — `MainActivity` itself no longer carries the `LAUNCHER` intent-filter, only the aliases do. The choice persists in `AppPreferences.useBlueAppIcon` (`StateFlow<Boolean>`, same pattern as `isDarkMode`) so the Settings toggle reflects the right side on reopen. Settings shows this as a White/Blue segmented toggle styled like `PreferredNameSelector`'s First/Middle segments (not a plain `Switch`) — the second deliberate reuse of that visual pattern outside its original component. Known quirk: switching aliases on an app already installed via adb can cause the launcher to show a stale/duplicate icon until the app is uninstalled and reinstalled — a launcher-cache artifact, not a data bug.

### Localization (English/Turkish)

Every user-facing string in the app lives in `res/values/strings.xml` (English, default) and `res/values-tr/strings.xml` (Turkish) — no hardcoded UI string literals remain anywhere in `ui/`. Common repeated words (Cancel/Save/Add/Delete/Name/Icon, etc.) are consolidated into shared `common_*`/`label_*` resources reused across screens rather than redefined per-dialog. **Trailing/leading spaces in a string resource are silently stripped by the XML parser unless the whole value is wrapped in double quotes** (`<string name="x">"prefix "</string>`, not `<string name="x">prefix </string>`) — bit the app once already (`home_welcome_prefix`'s space before the bolded name vanished, caught on-device) — any string a build-annotated/concatenated value depends on keeping edge whitespace needs this.

- **Free-text user data is never translated, with one deliberate exception: Course names.** Exam/topic/language/study-resource names, publishers, etc. always stay exactly as typed. Courses are different by explicit request: `ui/common/CourseNameDisplay.kt`'s `courseDisplayName(name: String): String` is a `@Composable` lookup, the same display-only-at-render-time pattern as `examTypeDisplayName()` — a fixed set of common subjects ("Geometry", "Biology", "Chemistry", etc.) translate for display (e.g. "Geometri", "Biyoloji", "Kimya"); any course name outside that list (a custom name, or "German A1"/"German A2"-style language-level course names that exist as leftover pre-Language-table data) just shows as typed, same as any other free text. Applied everywhere a course name is rendered read-only (list rows, checklists, screen/dialog titles, delete-confirmation messages) — **but deliberately not** to `CourseDetailScreen`'s `CourseEditDialog` `initialName` (the field you actually edit and save): translating that would mean saving the edit dialog without touching the name field silently overwrites the real English name with its Turkish display text, corrupting the underlying data. The drawer/menu word for the Courses feature itself was also renamed in Turkish from "Kurslar" to "Dersler" ("kurs" reads as an external training course, not an academic subject) — this only touched the `values-tr/strings.xml` chrome strings (`label_courses`, `dialog_add_course_title`, etc.), not the English default wording or any code/route/table naming.
- **`ExamType.name`/`LANGUAGE_EXAM_TYPE_NAME` stays English in the database and in all comparisons** — these are seeded DB rows (see `ExamTypeDao` above), not compile-time resources. `ui/common/ExamTypeDisplay.kt`'s `examTypeDisplayName(name: String): String` is a `@Composable` lookup (`when (name) { "University Entrance Exam" -> stringResource(...), ... }`) called only at the point of *display* — every place `examType.name`/`examTypeName` is rendered to the user wraps it in this; nothing ever compares against a translated value.
- **`ui/common/CourseIcons.kt`'s `CourseIconOption` stores a `@StringRes labelRes: Int`, not a raw `String`** — icon content descriptions need `stringResource()`, which requires a Composable context, but `CourseIcons.options` is a plain top-level `val` list; `CourseIconPicker` resolves `stringResource(option.labelRes)` at the point of use instead.
- **ViewModel-originated error messages** (login/register/profile-edit/switch-account validation) can't call `stringResource()` directly (`AndroidViewModel` isn't a Composable context) — they're modeled as `ui/common/ErrorMessage.kt`'s `ErrorMessage` enum (`INVALID_USERNAME_PASSWORD`, `USERNAME_TAKEN`, etc.), exposed as `StateFlow<ErrorMessage?>` from each ViewModel, and resolved to display text via `ErrorMessage.text()` (a `@Composable` extension) only in the Screen.
- **Category/type group-header labels vs. single-value labels use different fallback text for the unset case** — `ui/common/CourseCategoryLabel.kt` has two separate composables for this reason: `courseCategoryGroupLabel()` (null → "Uncategorized", used for the Quantitative/Verbal/Uncategorized group headers in `CourseListByTypeScreen`/`ExamDetailScreen`/`SectionDetailScreen`) and `courseCategoryValueLabel()` (null → "Not set", used for a single course's own category value in `CourseDetailScreen`) — conflating them into one function would show the wrong fallback word in one of the two places.
- **A composable that groups a `LazyColumn`'s items by category (or any enum) must NOT itself be `@Composable`** — `LazyListScope`'s builder body (the lambda passed to `LazyColumn { ... }`) is not a composable context, so calling `stringResource()`-based label functions there to compute group keys fails to compile. The fix used throughout (`ExamDetailScreen.examCourseGroups`, `SectionDetailScreen.sectionCourseGroups`, `CourseListByTypeScreen.courseGroups`): group by the raw enum/nullable key (e.g. `CourseCategory?`), keep the `mutableStateMapOf` expand-state keyed by that same raw enum (not by the translated display string, which would also be locale-dependent and require re-deriving the label a second time outside the composable `item {}` block just to read the map), and only call the label composable *inside* the `item { }` block where a real composable context exists.
- **Switching languages requires `Activity.recreate()`, not just a Compose-level override** — the first implementation tried wrapping `LocalContext` via `CompositionLocalProvider` in `MainActivity`'s `setContent`, which correctly re-localized ordinary screen content but silently left every `AlertDialog`/`DropdownMenu`/`DatePickerDialog` body and button text in the OS's real locale (confirmed on-device: a dialog's title — resolved in the caller's composition, before entering the dialog — translated correctly, while the exact same dialog's "Name"/"Icon"/"Cancel"/"Save" — resolved *inside* the dialog's own composable slots — did not). `Popup`/`Dialog` create their own Android `Window` and re-derive `LocalContext` from the real Activity context there, bypassing any ambient CompositionLocal override made further up the tree. The working fix: `MainActivity.attachBaseContext()` wraps the real base `Context` in a locale-adjusted `Configuration` (reading the persisted preference via a throwaway `AppPreferences(newBase)`), and `SettingsScreen` calls `LocalContext.current.findActivity()?.recreate()` (`ui/common/FindActivity.kt`) right after `viewModel.setAppLanguage(...)`. `recreate()` behaves like a configuration-change relaunch (same mechanism `AppCompatDelegate.setApplicationLocales()` uses internally) — confirmed on-device that it preserves navigation position, scroll/dialog state, and other Settings toggles (Dark mode, App Icon) across the switch, both directions.
- `AppPreferences.appLanguage: StateFlow<AppLanguage>` (`ENGLISH`/`TURKISH`) follows the same persisted-preference shape as `isDarkMode`/`useBlueAppIcon`, defaulting to Turkish only if the *system* locale is already Turkish at first launch, English otherwise. Setting it also calls `Locale.setDefault(...)` so `ui/common/DateFormatting.kt`'s `SimpleDateFormat("MMM d, yyyy", Locale.getDefault())` picks up correctly localized month names with no changes of its own needed. Settings shows this as an English/Turkish segmented toggle, the third reuse of the `PreferredNameSelector`/App-Icon segmented-toggle visual pattern.

### Navigation shell

`ui/shell/AppShell.kt` is the persistent chrome — a `ModalNavigationDrawer` (a 140dp-tall banner image, `drawable-xxxhdpi/drawer_banner.png` rendered via `Image(..., contentScale = ContentScale.Crop)`, clickable to go Home — then Exams, Courses, Study Resources, Languages, then a "Home" item pinned to the drawer's bottom via a `ColumnScope` weight spacer) and a `TopAppBar` with a hamburger (opens the drawer) and a three-dot overflow menu ("User Settings" → Edit Profile, "App Settings" → theme toggle, "Account" → opens a second dropdown with Log Out / Switch Account). All five drawer items (Exams, Courses, Study Resources, Languages, Home) carry a fixed `icon =` (`Icons.AutoMirrored.Filled.Assignment`, `Icons.AutoMirrored.Filled.MenuBook`, `Icons.Filled.Bookmark`, `Icons.Filled.Translate`, `Icons.Filled.Home` respectively) — Exams/Courses/Study Resources/Languages were added after Home already had one, to match. A thin `HorizontalDivider` separates *each* drawer destination from the next (Exams | Courses | Study Resources | Languages), not just as one divider lumping them all vs. Home — so a future destination added after Languages gets the same treatment; the overflow menu has the same divider between each of its entries, including before "Account". **Every** shell-level screen renders through it: `HomeScreen`, `ExamListScreen`, `CourseListScreen`, `StudyResourceHomeScreen`, `LanguageListScreen`, `UserEditScreen`, `SettingsScreen` all call `AppShell(navigation = shellNavigation, title = ...) { innerPadding -> ... }` instead of their own bare `Scaffold` — the menu is never absent on any of them, and none of them has a back-arrow icon anymore (getting back to Home is via the drawer, not a back button; the Android system back gesture still works normally through the nav back stack). `ShellNavigation` (also in `AppShell.kt`) bundles the seven `onNavigate*` callbacks (including `onNavigateStudyResources`) plus `onLogOut`/`onSwitchAccount`, and is threaded through `TargetNavHost` into each of these screens' composable calls.

**Log Out / Switch Account**: the overflow menu's "Account" item opens a second `DropdownMenu` (state: `accountMenuExpanded`, separate from the main `overflowExpanded`) with two entries — Log Out and Switch Account. Log Out (`TargetNavHost`'s `signOut` lambda) sets `AppPreferences.currentUserId = null` and navigates to `LoginRoute` with `popUpTo(0)`, clearing the whole back stack. Switch Account navigates to `SwitchAccountRoute` (`ui/switchaccount/SwitchAccountScreen.kt` + `SwitchAccountViewModel.kt`) — a back-arrow `Scaffold` (not `AppShell`, since it's a drill-down from the overflow menu, not a drawer destination) listing every other `User` row on the device (`UserDao.getAll()`, filtered to exclude the current session's id). Tapping one opens a password-confirmation `AlertDialog` — switching accounts re-verifies the target account's own password via `PasswordHasher.verify()` before setting `AppPreferences.currentUserId`, the same trust boundary as logging in fresh, rather than letting a signed-in session hop into another account without proof of that account's credentials. On success it navigates to `HomeRoute` with `popUpTo(0)`, same full-reset pattern as Log Out.

`HomeScreen`'s welcome text bolds just the preferred name (`buildAnnotatedString` + `SpanStyle(fontWeight = FontWeight.Bold)` around `currentUser?.preferredName`, "Welcome to Target, " stays regular weight) — the one place in the app a single string mixes font weights inline rather than being a single `Text` call.

`ExamDetailScreen` and `SectionDetailScreen` are the deliberate exception — reached by drilling into a *specific* exam/section (not a drawer destination), they keep their own simple back-arrow `Scaffold` as before, not `AppShell`. `CourseListByTypeScreen`, `LanguageExamCoursesScreen`, `CourseDetailScreen`, `LanguageDetailScreen`, `CourseStudyResourceScreen`, `LanguageStudyResourceScreen`, `StudyResourceDetailScreen`, `TopicListScreen`, and `TopicDetailScreen` follow the same exception, since each is reached by drilling into a specific bucket/course/language/resource/topic from either `CourseListScreen`, `StudyResourceHomeScreen`, or `CourseDetailScreen`, not from the drawer directly.

Drawer/overflow navigation between the six shell-level destinations uses `popUpTo<HomeRoute> { saveState = true }` + `launchSingleTop = true` + `restoreState = true` (a private `NavHostController.navigateToShellDestination()` extension in `TargetNavHost.kt`) — bouncing between Exams/Courses/Study Resources/Languages/User/Settings via the menu doesn't pile up back-stack entries the way plain repeated `navigate()` calls would.

Screen shape: `LoginScreen`/`RegisterScreen` → `HomeScreen` → `ExamListScreen` → `ExamDetailScreen` (edit/delete exam; Courses list hidden on Language Exams and on sectioned exams — see above for both; Sections shown when `hasSections`) → `SectionDetailScreen` (edit/delete section; course-subset picker, rows tap through to `CourseDetailScreen` same as `ExamDetailScreen`'s pool); `CourseListScreen`, `StudyResourceHomeScreen`, `LanguageListScreen`, `UserEditScreen`, `SettingsScreen` reachable from any shell screen's drawer/overflow menu, not just Home's. `CourseListScreen` drills into `CourseListByTypeScreen` → `CourseDetailScreen` → `CourseStudyResourceScreen` and `LanguageExamCoursesScreen` → `LanguageDetailScreen` → `LanguageStudyResourceScreen` (edit/delete live on the Detail screens); `StudyResourceHomeScreen` drills into its own `CourseListByTypeScreen`/`LanguageExamCoursesScreen` instances (via `StudyResourceCourseListByTypeRoute`/`StudyResourceLanguageExamCoursesRoute`) that skip straight to `CourseStudyResourceScreen`/`LanguageStudyResourceScreen`, bypassing Detail — Study Resources is a shortcut to the study-resource list, not a second route into Detail. The drawer's `LanguageListScreen` also feeds into `LanguageDetailScreen`, same as the Courses flow. Add/Edit exam share one dialog, `ui/common/ExamFormDialog.kt`'s `AddOrEditExamDialog` — it's non-trivial (name field, exam-type picker, has-sections switch, conditional date picker(s)) so it's the one deliberate exception to this app's usual "duplicate small dialogs per screen" pattern (the other being `PreferredNameSelector`, above).

Forms with more than a couple of fields need `Modifier.imePadding()` on their scrollable content column, or the on-screen keyboard covers whatever's focused — `enableEdgeToEdge()` plus a manifest `windowSoftInputMode="adjustResize"` alone isn't sufficient in Compose. All of `LoginScreen`/`RegisterScreen`/`UserEditScreen` have it; apply it to any new multi-field form too.
